# P6.1 — Deployment preflight, and the smallest architecture that closes G6

**Status: the deployment is defined, committed and blocked on IAM. Nothing has been created in
AWS. No resource exists, no bill has started, and G6 is not claimed to be closed or advanced
beyond this preparation.**

P6 opens with one question that has to be answered before anything is built: can the credential
this project actually holds create the deployment G6 describes? The answer is no, and it is no
by a wide margin — the role can invoke one Bedrock model and read its own identity, and nothing
else. So this slice does the work that does not depend on the answer: it establishes the
boundary reproducibly, chooses the architecture, writes the whole deployment definition, and
states the exact permission delta needed to run it. The mutation itself waits for a decision
only the account owner can make.

## 1. IAM preflight result

The active identity is the expected one, and it is not root:

```
arn:aws:sts::<ACCOUNT_ID>:assumed-role/PromisePatchDeveloperRole/PromisePatchLocalDevelopment
region us-east-1
```

The account number is redacted here and placeholdered in the policy documents for the same
reason: this repository becomes a public clone at G9, and an account id is an enumeration
target. The preflight prints the real value when it runs.

`scripts/aws_preflight.py` is the reproducible form of this check. It is read-only by
construction rather than by promise: every requirement names the AWS API behind it, and a
requirement carrying a probe must name an API in a frozen `READ_ONLY_APIS` set — one that does
not raises `MutatingProbeError` and aborts the run, so the script cannot grow a resource-creating
call without that list changing in a reviewable diff. `test_a_probe_on_an_undeclared_api_aborts_the_run`
exercises that guard by smuggling an `ec2:RunInstances` probe past it and asserting the refusal.

Run it with:

```bash
uv run python scripts/aws_preflight.py
```

**Result: 2 of 9 required permissions allowed.**

| Plane | Requirement | Verdict |
|---|---|---|
| preflight | `sts:GetCallerIdentity` | **ALLOWED** |
| preflight | `iam:SimulatePrincipalPolicy` | DENIED *(informational)* |
| preflight | `bedrock:GetFoundationModel` | DENIED *(informational)* |
| deployment | `cloudformation:ListStacks` | **DENIED** `AccessDenied` |
| deployment | `iam:ListRoles` | **DENIED** `AccessDenied` |
| deployment | `ec2:DescribeVpcs` | **DENIED** `UnauthorizedOperation` |
| deployment | `ecr:DescribeRepositories` | **DENIED** `AccessDeniedException` |
| deployment | `rds:DescribeDBInstances` | **DENIED** `AccessDenied` |
| deployment | `ssm:DescribeParameters` | **DENIED** `AccessDeniedException` |
| deployment | `logs:DescribeLogGroups` | **DENIED** `AccessDeniedException` |
| runtime | `bedrock:InvokeModel` on `inference-profile/us.amazon.nova-2-lite-v1:0` | **ALLOWED** |

Twelve further mutating requirements are reported `DECLARED` rather than tested. That is a
limitation stated as one: a mutating permission cannot be proved without mutating, and
`iam:SimulatePrincipalPolicy` — the API that exists precisely to answer this without side
effects — is itself denied. What the table does establish is stronger than it looks: when a
service's *read* is denied, the role has no access to that service at all, so every declared
mutation against it is blocked with it.

Three details worth recording, because each would have cost time to rediscover:

- **The role cannot read its own policy.** `iam:GetRole`, `iam:ListRolePolicies` and
  `iam:ListAttachedRolePolicies` are all denied, so the preflight had to be behavioural rather
  than a policy inspection.
- **The Bedrock permission is scoped to one inference profile, not to a model family.**
  `bedrock:InvokeModel` on `us.amazon.nova-2-lite-v1:0` is allowed; the same action on
  `us.amazon.nova-lite-v1:0` is denied, and so is the control-plane
  `bedrock:GetFoundationModel`. The runtime role in the template mirrors that scoping exactly,
  and names both the inference-profile ARN and the foundation-model ARNs in the three regions a
  US cross-region profile may route to — scoping to the profile alone produces a denial at call
  time.
- **The account is not subscribed to App Runner.** `apprunner:ListServices` returns
  `SubscriptionRequiredException` rather than `AccessDenied`, which removes the one option that
  would have supplied managed HTTPS without a certificate of our own.

The `bedrock:InvokeModel` probe deserves its own note. There is no read-only way to ask whether
an identity may invoke a model, so the probe sends a body that cannot possibly be valid (`{}`)
and reads the error class: `AccessDeniedException` means no, `ValidationException` means yes —
authorization passed and the request was then rejected for its shape. No inference ran, no
tokens were consumed, and nothing was billed for the entire preflight.

## 2. The permission blocker, stated before anything is changed

**No AWS resource may be created with the current role, and none was.** The role is a
Bedrock-runtime role; it holds no deployment plane at all. IAM was not broadened, no policy was
attached, and `AdministratorAccess` was neither used nor requested.

The ask is deliberately shaped so that a person ends up with almost no standing privilege. All
mutation goes through one CloudFormation stack executed with a service role that only
CloudFormation can assume. A human holding the delta below cannot create an EC2 instance, an
RDS database or an IAM role by hand.

### 2.1 Three roles, one job each

| Role | Who holds it | What it is for | Lifetime |
|---|---|---|---|
| `PromisePatchDeveloperRole` | a person, locally | submit and read one stack; push images; write secrets; restart the host | permanent, tiny |
| `PromisePatchDeploymentRole` | CloudFormation only | create the compute, database, network, log and runtime-role resources | permanent, unreachable by people |
| `PromisePatchInstanceRole` | the EC2 host | pull images, read its own secrets, ship logs, invoke one model | as long as the deployment runs |

The two `iam:PassRole` grants are the narrowest form each can take, and both are additionally
fenced by an explicit `Deny` with `NotResource`, which no later `Allow` can override:

- the person may pass **only** `PromisePatchDeploymentRole`, and only when
  `iam:PassedToService` is `cloudformation.amazonaws.com`;
- the deployment role may pass **only** `PromisePatchInstanceRole`, and only when
  `iam:PassedToService` is `ec2.amazonaws.com`.

### 2.2 The exact policy documents

Committed, with `ACCOUNT_ID` as a placeholder because the repository becomes public at G9 (a
test fails on a literal twelve-digit account id in any of them):

- `deploy/policies/developer-role-delta.json` — attach to `PromisePatchDeveloperRole`
- `deploy/policies/deployment-role-trust.json` — the trust policy for the new service role
- `deploy/policies/deployment-role-policy.json` — that role's permissions

### 2.3 What each grant is for, and which plane it belongs to

**Deployment-only** — revocable the moment the stack exists and the demo is recorded:

| Actions | Resource | Why |
|---|---|---|
| `cloudformation:` Create/Update/Delete/Describe/ChangeSet | `stack/promisepatch-*/*` | the stack is the only mutation path; without this nothing can be created or read back |
| `iam:PassRole` | `role/PromisePatchDeploymentRole`, service `cloudformation` | hand the stack its service role and nothing else |
| `ecr:` CreateRepository, PutLifecyclePolicy, layer upload, PutImage | `repository/promisepatch/*` | an image push is not a CloudFormation action, and the registry must exist before the host boots |
| `ecr:GetAuthorizationToken` | `*` | the registry auth token has no resource form; it is a read |
| `ssm:PutParameter`, `DeleteParameter` | `parameter/promisepatch/*` | write the database password, bearer token, session secret and webhook secret |
| `kms:` Encrypt/Decrypt/GenerateDataKey | `*` with `kms:ViaService = ssm.us-east-1` | encrypt those SecureStrings, and only through SSM |
| `logs:` Describe/Get/Filter/StartLiveTail | `log-group:/promisepatch/*` | read the deployed loop back out |
| `ec2:` Reboot/Stop/StartInstances | `instance/*` with `ResourceTag/Project=promisepatch` | the restart-durability proof needs to restart the host |
| `ssm:StartSession` and friends | tag-scoped | reach the host with no inbound SSH and no key pair |
| a read-only list of `ec2/rds/iam/ssm` Describes, plus `pricing:GetProducts` and `ce:GetCostAndUsage` | `*` | the preflight itself, and reading the real bill instead of estimating it |

**Runtime-only** — held by the instance profile, created by the stack, never by a person:

| Actions | Resource | Why |
|---|---|---|
| `ecr:` BatchGetImage, GetDownloadUrlForLayer, BatchCheckLayerAvailability | the two `promisepatch/*` repositories | pull images at boot and again after a restart |
| `ssm:GetParameter(s)`, `GetParametersByPath` | `parameter/promisepatch/<env>/*` | read its own secrets at boot; none are baked into an image or an AMI |
| `kms:Decrypt` | `*` with `kms:ViaService = ssm` | decrypt exactly those |
| `logs:CreateLogStream`, `PutLogEvents` | `log-group:/promisepatch/<env>` | container output leaves the host, so a restart cannot erase the evidence |
| `bedrock:InvokeModel` | the one inference profile plus its three foundation-model ARNs | the orchestrator's one semantic call |
| `AmazonSSMManagedInstanceCore` (managed) | — | the only managed policy anywhere in the stack; it buys a host with no SSH port and no key pair |

The deployment role additionally carries three caps that exist so a mistake cannot become
expensive or exposed: `ec2:RunInstances` is denied for any instance type outside
`t4g.small`/`t4g.medium`/`t3a.small`/`t3a.medium`, `rds:CreateDBInstance` is denied for any
class outside `db.t4g.micro`/`db.t4g.small`, and both RDS actions are denied outright when
`rds:PubliclyAccessible` is true.

## 3. The deployed architecture

```
internet ──443──▶ caddy (TLS) ──▶ api ──┬──▶ RDS PostgreSQL (private, encrypted)
                    │                   └──▶ Bedrock (one inference profile)
                    ├──▶ mcp ──authenticated HTTP──▶ api
                    └──▶ order-simulator ──signed webhook──▶ api
                                         (its own SQLite file, its own volume)
         worker ──▶ RDS   (no listening socket; restarting it is the recovery mechanism)
```

**Six AWS services, each with a stated job.** EC2 (one instance, one EBS root volume, two
security groups, one Elastic IP), RDS for PostgreSQL, ECR for two images, SSM Parameter Store
for secrets and configuration, CloudWatch Logs for output, and Bedrock for the one semantic
call. There is no load balancer, no NAT gateway, no ECS control plane, no Secrets Manager and
no CloudFront. `deploy/cloudformation/promisepatch.yaml` is the whole definition: twelve
resources, eleven parameters, eight outputs.

**Why one host rather than five services.** The authority boundary this product rests on is not
a network boundary and would not be strengthened by becoming one. `mcp` is given no database
URL and cannot import the domain — that is enforced by an import-linter contract and by which
environment file each container receives — so it reaches a case only by an authenticated call
to `api`. Splitting the containers across five AWS services would add a load balancer, task
definitions and a NAT gateway to a deployment whose job is to prove one loop survives outside a
laptop. The state is what genuinely cannot stay on the host, and it does not: the case state and
the step ledger are in RDS.

The deployed containers run the same images with the same commands and the same per-container
environment files as the local stack. Nothing in the backend was redesigned for the cloud; the
only application-visible differences are where the database is, that a TLS terminator is in
front, and that logs go to CloudWatch instead of a terminal.

### 3.1 TLS

Caddy terminates TLS with an automatically issued, publicly trusted certificate for a hostname
supplied as a stack parameter, and holds the certificate on a named volume so a restart does not
re-order one. It makes no authorization decision, adds no header the backend trusts and strips
nothing the backend needs: the MCP server's bearer check, `Origin` allowlist and `Host`
validation stay in the `mcp` process where P5.1 put them, in front of the protocol. `/mcp` and
`/events` are proxied with response buffering disabled, because buffering would hold a
server-sent event until the response completed and turn a stream into a single late block.

Certificate verification is never weakened anywhere. A parametrised test enumerates thirteen
spellings of "trust whatever certificate turns up" — `verify=False`, `--insecure`,
`--no-verify-ssl`, `InsecureSkipVerify`, `CERT_NONE` and the rest — and fails on any of them
appearing in non-comment content anywhere under `deploy/` or in either deployment script.

**This needs a DNS name.** A publicly trusted certificate cannot be issued for an
`ec2-*.compute-1.amazonaws.com` name, and an ACM certificate needs a domain to validate
against. `TlsHostname` is therefore a required parameter with no default, and a DNS A record
must point at the stack's `ElasticIp` output before the host finishes booting. **This is the one
open input the account owner has to supply**, and it is listed again in §8.

### 3.2 Secrets

Every secret is an SSM `SecureString` under `/promisepatch/<env>/`, generated by
`deploy/deploy.sh secrets` with `--no-overwrite` so a re-run cannot rotate a live database
password out from under a running instance. None is a stack parameter, none appears in a
CloudFormation event, none is committed and none is baked into an image: the database master
password reaches RDS through a `{{resolve:ssm-secure:...}}` dynamic reference, and the host
reads the rest at boot with its instance role. The environment files are written under
`umask 0077` into a `0750` directory.

Two non-secret parameters carry the deployed composition and the Caddyfile. Both live in git and
are uploaded from there, so the host re-reads both at every boot and changing either is a
parameter write plus a restart rather than an instance replacement. Both must stay under 4096
bytes to fit a standard-tier parameter; a test asserts it, and `deploy.sh config` refuses to
upload a file that has outgrown it.

### 3.3 Persistence

| What | Where | Survives |
|---|---|---|
| case state, step ledger, audit rows, consent | RDS PostgreSQL, gp3, encrypted, 7-day backups | container restart, instance stop/start, instance replacement, stack deletion (`DeletionPolicy: Snapshot`) |
| the separate order system's orders and events | SQLite on a named Docker volume on the host | container restart, instance reboot — **not** instance replacement |
| the certificate and ACME account key | named Docker volume | container restart, instance reboot |
| container output | CloudWatch Logs, 14-day retention | everything above |

The order simulator's store is on a host volume rather than its own durable service, and that is
a deliberate limit rather than an oversight: it is a *separate* store, which is what the
architecture claims, and replacing the instance loses it. Recording that plainly matters more
than the alternative, which would be a second RDS instance for a simulator.

### 3.4 Egress

The host security group's egress is a closed list, not the default allow-all: TCP 443 to
anywhere — Bedrock, ECR, SSM, CloudWatch Logs, the ACME directory and the public image
registries are all 443 — plus TCP 5432 to the database security group and nothing else.
Ingress is 443 and 80 only; 80 carries the ACME challenge and a redirect. There is no port 22
and no key pair, because access is Session Manager. The database's group accepts 5432 from the
host group by security-group reference rather than by CIDR, is not publicly accessible, and
initiates nothing.

The host is in a public subnet with an Elastic IP rather than a private subnet behind a NAT
gateway. That is a cost decision made explicitly — a NAT gateway is the single largest line item
this architecture could have had — and the security group is what limits the exposure.

**One consequence has to be stated exactly, because the honest description is weaker than the
tempting one.** An instance in a VPC has no route back to its own public address, so the order
simulator cannot reach the deployment by its public name over the internet. It resolves that
name to the TLS proxy on the same host via a fixed container address. The handshake, the SNI,
the certificate and its verification are all real, and the webhook signature is verified exactly
as it would be otherwise — but the packet does not leave the host. It is a real TLS hop, not a
real internet hop. Putting the simulator on its own instance is what would make it both, and
that is named as a gap in §8 rather than glossed here.

## 4. Restart and durability

The design intent is that the case outlives every process: `worker` holds no state but a row,
`SIGTERM` ends its current cycle and a hard kill leaves leases that expire, `restart:
unless-stopped` is the recovery mechanism, and a systemd unit brings the composition back after
an instance reboot without re-running the bootstrap. The instance's user data is idempotent and
runs on every boot, so a restarted or replaced host converges on the same deployment rather than
on whatever was left behind.

**No restart proof has been executed, because there is nothing deployed to restart.** The
deployment-role and developer-delta policies both include the instance restart actions
specifically so this proof can be taken as the first act after the permissions land. What it
will consist of is fixed now, so it cannot be chosen after the fact to suit the result: reach a
case to `PLANNED` over the deployed MCP endpoint, restart the host, and read the same case id
back at the same state with the same step ledger and no duplicated effect.

## 5. The canonical deployed loop

**Not run. No deployment exists.** The local canonical conversation and the local recovery path
are closed under P5.3 and P5.4 and are unchanged by this slice; nothing here reopens them and
nothing here claims a deployed equivalent. `scripts/deployment_smoke.py` is the check that will
be run against the deployed origin first, and it is written to fail a deployment that comes up
*too permissive* rather than only one that is down — an unauthenticated `POST /mcp` must be
`401`, an unlisted `Origin` `403`, an unlisted `Host` `421`, an unsigned order-system event
refused, and the `initialize` handshake must negotiate exactly `2025-11-25`. A test asserts that
pinned revision equals the server's own `PROTOCOL_REVISION` constant, so the smoke check cannot
drift off the surface it is checking. It has never been run against a live endpoint, because
there is none.

**Roughly $33 per month of standing cost.** The single largest saving in the architecture is
the one line item that is absent: a NAT gateway would have cost more than the host and the
database combined, and the host sits in a public subnet behind a closed egress list instead.

An idle deployment is not free and is not much cheaper: stopping the instance removes $12.26
and leaves the database, the volume and the address. Deleting the stack leaves the ECR images
and a final database snapshot.

**Bedrock is the only per-use cost, and it is measurable rather than estimated.** From the one
bounded live Nova conversation recorded in P5.3 — six turns, 10,360 input and 165 output tokens
— at the list rates for `USE1-Nova2.0Lite-input-tokens` ($0.00033 per 1K) and
`USE1-Nova2.0Lite-output-tokens` ($0.00275 per 1K):

```
10.360 × $0.00033  +  0.165 × $0.00275  =  $0.00342 + $0.00045  ≈  $0.0039 per conversation
```

That is arithmetic over a measured token count at a published rate, not a projection. It is also
why no dollar figure was published for that run at the time: the rate could not be verified from
the account then, and it still cannot — this is the list price, and the account's own charge may
differ.

The two capped instance classes in the deployment role's policy exist so that this cost model
cannot be quietly invalidated by someone launching something larger.

## 7. AgentCore decision — **not used, ordinary AWS compute instead**

The roadmap makes AgentCore a SHOULD with a one-engineer-day feasibility budget and an explicit
instruction to record the real obstacle and fall back rather than hold the schedule hostage.
Three obstacles, the first of them decisive:

1. **The role cannot reach it.** `bedrock-agentcore-control:ListAgentRuntimes` returns
   `AccessDeniedException`. Adopting AgentCore would mean asking for a second, differently
   shaped permission set on top of the one this document already asks for, and waiting on both.
2. **It would replace an authority boundary that is already closed.** The authenticated
   Streamable HTTP surface — bearer check in front of the protocol, `Origin` allowlist, `Host`
   validation, protocol revision `2025-11-25` pinned, worker identity owned by the server — is
   part of the non-negotiable G5 deployment-entry subset that closed at `e59e953`. AgentCore
   Runtime brings its own identity and authentication model, so hosting the same server there
   is not a lift-and-shift: it is a change to the surface G5 signed off, and it would have to be
   re-proved.
3. **It buys nothing this slice is short of.** The value AgentCore would add is managed hosting,
   managed auth and traces. Hosting is one EC2 instance here; auth exists and is audited; and
   correlated identifiers already reach the governed audit row from every tool call, with
   container output going to CloudWatch Logs.

The roadmap's ordinary AWS compute fallback is therefore taken deliberately and on the first
day, not after a day was spent failing. The stale claim that AgentCore requires a stateless
server is not the reason — current AWS documentation supports both, and stateless remains the
right choice here because business state belongs in PostgreSQL. Should AgentCore be revisited,
the thing to revisit is hosting the same `pp mcp` process behind it, with the bearer check
intact.

## 8. Remaining G6 gaps

Nothing in G6 is closed. Ordered by what blocks what:

1. **The IAM delta is unapplied.** Every item below waits on it. It is the only blocker that
   cannot be resolved from inside this repository.
2. **A DNS name.** `TlsHostname` has no default and a publicly trusted certificate cannot be
   issued without one. The account owner supplies either a domain they control or a wildcard-DNS
   name resolving to the Elastic IP; the template is identical either way.
3. **Nothing is deployed.** No stack, no host, no database, no image pushed.
4. **The restart proof is designed and not taken** (§4).
5. **The canonical deployed conversation has not run** (§5), and the deployment smoke checks
   have never met a live endpoint.
6. **The real customer loop is absent.** G6 requires a known customer on a second device —
   request, nonliteral reply, one deterministic confirmation, literal `YES`/`NO`, with provider
   message identity and the wrong-sender, invalid-secret, duplicate-update and expiry cases
   preserving authority and idempotence. No Telegram work was done here, per the instruction not
   to implement it unless the deployment spine required it. It did not.
7. **The evidence UI is not deployed.** `docker/Dockerfile.frontend` runs a Vite dev server; a
   static build stage is needed before Caddy can serve the P5.4 workspace. G6 does not require
   it, but the pending-versus-completed distinction is more legible with it.
8. **The order simulator shares the host** (§3.4). Its webhook crosses real TLS but not the
   public internet, and its store does not survive instance replacement.
9. **Cost is list-price arithmetic, not a bill** (§6), and two meters are named rather than
   priced.

Carried forward unchanged from the G5 closeout, and untouched here: the bounded withdrawal,
the runtime customer-intent classifier removal, and the finishing of the case workspace all
remain G7 obligations.

## 9. The next P6 slice, exactly

**P6.2 — first deployed stack and smoke.** Preconditions: the three policy documents applied by
the account owner with `ACCOUNT_ID` substituted, and a DNS name for `TlsHostname`.

1. Re-run `uv run python scripts/aws_preflight.py`. It must print `9/9 required allowed` and
   exit 0. If it does not, stop and report the remaining denial — no stage of `deploy.sh` runs
   past a failed preflight, by construction.
2. `./deploy/deploy.sh secrets registry images config` — in that order, for the reason given in
   the script's header: the registry must exist before a push, and the images and configuration
   must exist before the host's first `compose pull`.
3. Point the DNS A record at the stack's `ElasticIp` output, then `./deploy/deploy.sh stack`.
4. `./deploy/deploy.sh smoke`. Seven checks, four of them refusals. Record the output verbatim,
   including any failure, before repairing anything.
5. Take the restart proof as specified in §4, and record the real monthly cost from
   `ce:GetCostAndUsage` once a full day has been billed.

Only then does P6.3 — the real customer loop over Telegram — begin. Local work that does not
depend on the deployment can proceed in parallel: the frontend static build stage (gap 7) is the
obvious candidate, and it is the one that makes the deployed truthfulness visible rather than
merely assertable.
