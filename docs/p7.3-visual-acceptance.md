# P7.3 — visual acceptance against the deployed product

The judge-facing surface was accepted against the [P7.1 UX contract](p7.1-judge-ux-contract.md)
and the [design handoff](p7.1-design-handoff.md)'s §9 list by driving the **real product** —
the deployed stack at `https://184.194.40.87.sslip.io` and a local stack running the same
committed code — through every state a judge can meet, at 1440×900, 1280×800, tablet and phone.

Five defects were found and fixed. Two design-acceptance items are **not** met and are recorded
here rather than worked around. Nothing was staged, mocked or composed for a screenshot: every
frame below is a durable case the machinery produced.

---

## 1. The five defects, and what each one was

Each was found by reading the rendered surface, not the source, and each has a test.

| # | defect | where it really was | commit |
|---|---|---|---|
| 1 | A deadline read out as `2026-09-13T23:35:32.020039+00:00` — in the spoken status a worker *hears*, and again in the `next_action` sentence | `domain/status_view`, not the screen. The screen was delivering the domain's string as given, which is the rule | `c5fa4b7` |
| 2 | `1 ORDERS AFFECTED` on any single-order case — the first thing a reader sees | `Count`, which had no wording for one | `660a981` |
| 3 | At 1280×800 the conversation panel filled the fold and **bands 3 and 4 began below it**, so the one comparison this product exists to show was not on the first screen | the band stack, which was one column at every width | `c403f73` |
| 4 | A case still asking its question published `0 left alone of 0 considered · 0 incident-caused effects` — this product's headline claim, made before any of the work that earns it | band 4, which drew the proof unconditionally | `f5b8441` |
| 5 | A deterministic reading showed its model as `unknown`, which reads as *we do not know which one* — the opposite of the claim | the technical record's absent-value fallback | `acfdd97` |

Two of these are worth naming as a class. **Defect 1 was fixed in the domain**, because the
contract forbids a screen re-wording what it was given: a machine timestamp in a human sentence
is the sentence's defect, not the renderer's. The structured `deadline_at` keeps its ISO form, so
each surface still renders that moment in its own reader's clock — the row already did, one line
above, which is how the duplication was spotted at all.

**Defect 4 was the domain being right and the screen not following.** `status_view` already
refuses to speak the untouched line on a case that has assessed nothing, for the reason its own
comment gives; the screen drew it anyway. A reader cannot tell a zero that was counted from a
zero that was merely not yet reached.

## 2. The 1280×800 measurement, and the item that is not met

Measured on the canonical four-promise case, same case and same server either side.

| | before | after |
|---|---|---|
| page height | 1721 | **1443** |
| conversation panel | 394 → 800, clipped at the fold | **145 → 815, whole** |
| band 3 begins | ~814 — at the fold | **~398** |
| untouched proof | 1428 | **1115** |

The panel moves beside the bands at `xl` and no higher, which is where the causal chain is
already horizontal; below that nothing changed, and the phone layout is byte-for-byte the one it
was. The document order is untouched, so reading order and the band sequence are unchanged — the
grid places the panel, the markup never moves it.

**What this does not achieve, and cannot without removing content.** The handoff's §9 asks that
each demo-critical frame compose in one unscrolled laptop viewport. Measured:

| frame | 1280×800 | 1440×900 |
|---|---|---|
| 1 · order book before anything | 2206 | — |
| 2 · the open question | 863 | **900 — fits exactly** |
| 3 · `PLANNED` in full | 1485 | 1487 |
| 4 · mid-recovery | 1485 | — |
| 5 · settled | 1509 | 1510 |

Four causal chains at four fixed columns are ~180px each; with the header, band 1, band 2 and
band 4 the floor is about 1120px before the conversation panel is counted at all. Reaching 800
means compressing the causal rows, which is the one thing on the screen a judge is meant to read.
**The content stays and the item is recorded as unmet.** Frame 3 is one scroll, not one screen.

## 3. The five demo-critical frames, captured from the real stack

Every one is a durable case reached through the real machinery — report, clarification, plan,
confirmation, recovery — with a real PostgreSQL, the real worker and the real External Order
System. None was arranged by writing state.

| frame | what it shows | evidence it is honest |
|---|---|---|
| 1 · order book | the six accepted promises with their constraints, and `no open case` on each | the empty state reads *"A case starts when somebody says what went wrong"* — not a command to run |
| 2 · the open question | `CLARIFYING`, the question as the focus, both options captured from the delivery's own rows | band 3 says *"Nothing has been decided about any promise yet"*, and band 4 now claims nothing at all |
| 3 · `PLANNED` in full | three authority lanes, four promises, the untouched pair, `4 orders affected / 2 left alone` | every promise reads *planned – waiting for you*; **no tick anywhere**, and the marker is a hollow square |
| 4 · mid-recovery | `WORKING`, `EXT-A` reading **changing the order now** | *"The order change has gone out and is not confirmed yet"* — caught live in a sub-second window, not staged |
| 5 · settled | `SETTLED`, `EXT-A` **changed**, the rest **needs you**, untouched 2, incident-caused effects **0** | the headline says *Finished.* while band 2 still says *3 promises below need the owner by hand* — a terminal case is not a claimed win |

Frame 4 was captured by polling the rendered surface while a confirmation ran; `APPLYING` lasts
well under a second, and the frame is the state that really existed rather than one held open.

On the local stack `EXT-B` escalates rather than being asked, because no customer-message
provider is configured there and the domain fails closed. The deployed stack, which has one,
produces the canonical `asked` — that reading is in §5.

## 4. The anti-pattern sweep

Run against the **shipped bundle** and against the rendered surface with every disclosure open,
as a judge and as a worker, on a `PLANNED` case.

| swept for | found |
|---|---|
| `devStage`, frame rails, a P7.3 badge, stage switcher, demo-mode toggle, `TODO`, `FIXME`, lorem | **none**, in source or in `dist/` |
| a tick, a completion mark, a green row on a `PLANNED` case | **none** |
| KPI, chart, trend, sparkline, activity feed, hours saved, revenue, satisfaction, orders rescued | **none** |
| generic chatbot framing | **none** |
| a UUID, enum, sequence number or hash in bands 1–4 | **none** |
| a disabled control for a capability that does not exist | **none** — zero disabled controls anywhere |
| an empty state instructing the reader to run a command | **none** |

The three occurrences of *done* on a `PLANNED` case are all negations — *"Nothing has been done
yet"*, *"before anything is done"*. The evidence drawer opens with **0 network requests**, which
is the committed rule and was re-proved here.

## 5. The deployed product

`https://184.194.40.87.sslip.io`, image `acfdd975dd4d`, which is the last commit of this work.

- **Deployment smoke: 11 of 12.** Five of the eleven assert a refusal. The one failure is
  `deployed-image`: the host serves `acfdd975dd4d` and the CloudFormation stack's `ImageTag`
  parameter still declares `87f3a13f26a9`. The release used `images → config → rollout`, which
  converges the host from SSM and **does not touch the stack parameter** — so the check is
  correctly reporting real drift between what is deployed and what the stack says is deployed.
  Closing it is a stack update, and it is the one item left open.
- `origin-refused` and `protocol-revision` initially reported 403-expected-401 and *skipped*.
  Both were an artifact of `PP_MCP_BEARER_TOKEN` being absent from the shell: without it the MCP
  endpoint answers `401` before it ever evaluates the `Origin`. With the token supplied, both
  pass. **Neither was a regression**, and the first run's failure is recorded here because a
  smoke result that changes when you export a variable is worth knowing about.
- **Browser gate: 42 of 42**, at 1440×900, 1280×800, tablet 768×1024 and phone 390×844,
  including the keyboard journey and the skip link.
- The fixes are live and were read back from the deployed host: the canonical case's spoken
  status says `asked, by 2026-09-13 23:35 (UTC)` with no ISO timestamp anywhere, while
  `deadline_at` keeps its machine form; a single-order case reads `1 ORDER AFFECTED`.
- Three cases **survived the release reboot**, which is the durability claim proved again
  incidentally.

### A false alarm worth writing down

Five accessibility tests failed against the local Docker frontend and did not fail against the
source. The frontend service has **no bind mount** — its image bakes the source in — so the
container had been serving a build from before this work the whole time, and the 20px skip-link
target it reported had already been fixed. Measured against a dev server on the working tree the
link is 1×1 unfocused and **136×44 focused**. The tests were right about the image and wrong
about the product, and the same staleness would have silently invalidated every local
measurement taken through that container.

## 7. What this did not do

- **No test was weakened, skipped or deleted.** Four suites gained tests: the deadline wording,
  the count vocabulary, the empty-case claim and the reading's provenance.
- **No IAM was created, changed or requested**, and nothing outside this project was touched.
- **No measurement is claimed** — no timing, no voice turn, no benchmark. The Alexa+ voice
  contract remains specified and unmeasured.
- **No live model call was made by this work.** The deployed Bedrock evidence is P6.2's and
  Session H's, unchanged.
- The `ImageTag` stack parameter was **not** updated, so the deployment declares an older tag
  than it serves.
