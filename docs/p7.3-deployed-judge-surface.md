# P7.3 — the judge surface, deployed

The redesigned surface is served from the deployed host, and a judge reaches a real case over
TLS in one action. This page records what is deployed, what had to change to deploy it, the two
defects the deployment itself found, and the evidence for every claim made here.

It records one slice of P7.3's implementation. Final visual acceptance, the demo capture and the
removal of the prototype directory are not part of it and are not claimed.

## 2. What changed, and why

### 2.1 The backend image carries the page

[ADR-0012](adr/0012-spa-served-by-the-deployed-host.md) has the decision and the arithmetic that
forced it: the deployed composition had 44 bytes of headroom under a hard 4096-byte parameter
limit, and the instance role's registry read names exactly two repositories. A seventh service
would have needed both to move. The backend image gained a Node build stage whose only output is
`dist/`, the API mounts it last, and one image tag now moves the whole surface.

The API owns its own paths and the page never answers for them: `/api`, `/events`, `/internal`,
`/healthz`, `/readyz`, `/docs`, `/redoc` and `/openapi.json` are enumerated in
[`api/spa.py`](../apps/backend/src/promisepatch/api/spa.py), and a request under any of them gets
the API's JSON `404`. Hashed assets are `immutable`; `index.html` is `no-store`.

### 2.2 The reverse proxy stopped being an allowlist

`/internal/intents/*` used to be unreachable from the public name **by accident**: the Caddyfile
named what it served and answered `404` to everything else. Serving the page needs a catch-all,
which ends that. The refusal is now written down — `handle /internal* { respond 404 }` — and
[`scripts/deployment_smoke.py`](../scripts/deployment_smoke.py) asserts it against the running
deployment, because a line somebody wrote is a line somebody can delete.

Caddy compiles `handle` blocks most-specific-first, so the path matcher beats the catch-all
whatever order they are written in. That was checked with `caddy adapt` rather than assumed; the
committed test asserts the written order too, because a refusal written below the thing it
refuses reads as dead code to whoever tidies it next.

### 2.3 A release now reaches the host

This is the defect P6.2 recorded and did not fix. cloud-init's `scripts-user` runs once per
instance, and `UserData` is not a replacement trigger for `AWS::EC2::Instance` — so a stack
update carrying a new `ImageTag` reported `UPDATE_COMPLETE`, left the instance id alone, and the
host went on serving the image it first booted with.

Three things close it:

1. **`converge.sh`**, written by the bootstrap and run by the systemd unit at **every** boot. It
   re-reads the composition, the TLS configuration and the image tag from SSM, rewrites
   `env/stack.env`, pulls and brings the stack up. It never seeds.
2. **`/promisepatch/<env>/image-tag`**, uploaded by `deploy.sh config` from the same commit that
   `deploy.sh images` pushed. That is what the host converges on.
3. **`deploy.sh rollout`**, which reboots the host and then reads `/healthz` back until it names
   the commit that was pushed — and fails if it never does. "The stack updated" and "the host is
   serving that build" are different claims, and the first was true while the second was false
   for a whole release.

The image reports its own identity because `deploy.sh images` passes `--build-arg PP_IMAGE_TAG`
and the runtime stage keeps it. `deploy.sh smoke` reads the stack's `ImageTag` parameter and
compares it with what the deployed process says it is, so drift is a failed check rather than
something somebody has to think to look for.

### 2.4 The judge entry is served here and nowhere else by default

`PP_DEMO_SESSION_ENABLED=true` is written into the deployed `api.env` and the model's default
stays `False`, so the scoped observer session is a deliberate choice for this deployment rather
than a standing unauthenticated endpoint in every copy of the repository. What it issues is a
session naming the seeded observer, whom the domain admits to case reads and refuses every write
([ADR-0013](adr/0013-read-only-observer-principal.md)).

## 3. What the deployment found that reading could not

### 3.1 The bootstrap lost its working directory

The first host of this release came up serving the new image, and its database had never been
seeded: `POST /api/auth/demo-session` answered `503 DEMO_SESSION_UNAVAILABLE`, because the
observer row is part of the fixture and the fixture had not been loaded.

The cause was one deleted line. Moving the composition fetch into `converge.sh` also removed the
`cd /opt/promisepatch` that used to precede it, so `docker compose run --rm -T seed` ran from
`/`, compose found no composition, and `set -e` took the rest of the bootstrap with it —
**including the systemd unit, which had not been written yet**. That host would have served until
its next boot and never converged again.

Two fixes, and a test for each:

- the seed runs from the project directory, and a test walks the bootstrap asserting no
  `docker compose` line appears before anything enters `/opt/promisepatch`;
- the unit is installed **before** anything that can fail, with `systemctl enable --now`, so the
  first boot brings the stack up exactly the way every later boot does — and a test asserts that
  ordering, naming `systemctl enable --now promisepatch` precisely, because
  `systemctl enable --now docker` appears earlier and a looser search finds that instead.

A third test extracts `converge.sh` from the template and parses it with `bash -n`. Nothing else
before a real host does: CloudFormation checks the template, not the shell it carries.

### 3.2 Replacing an instance on purpose

Both fixes had to reach a host whose files were written at its single boot, so the instance had
to be replaced — and CloudFormation offers no reliable way to ask for that. A change to
`UserData` is reported by a change set as `Conditionally`, and so is a change to `AdditionalInfo`;
both were observed resolving to an in-place modification that leaves the instance id alone and
the disk untouched. **Changing the resource's logical name is the only mechanism reported as an
unconditional Add and Remove**, and it was verified on a change set before anything was executed.

The name moved twice — `Host` → `AppHost` → `Host` — once to install the per-boot convergence and
once to fix the bootstrap that installed it. Now that the host converges from SSM at every boot,
a release is a parameter write and a reboot, and the name should not have to move again.

**Each replacement cost two things, and both are stated rather than buried.** A replaced host
re-runs the fixture seed, so the six cases P6.2 left on the deployment were erased; they were read
out and kept before the first replacement, and nothing but demo data was in them. And a replaced
host holds no certificate, so Let's Encrypt issued a new one each time — three issuances for this
name against a duplicate-certificate limit of five a week, which is why the next change must not
be another replacement.

### 4.3 A real Bedrock call, and what it did not buy

The canonical case is resolved by the deterministic path and calls no model — its evidence says
`source: DETERMINISTIC`, `provider: null`. So the model path was exercised deliberately, with an
utterance the deterministic path cannot ground: *"the chiller packed in overnight and everything
in it is ruined"*. Case `e66c5060-fddd-5724-b846-6c75af70e462`:

```
source:   SEMANTIC_ASSISTED      provider: bedrock
model_id: us.amazon.nova-2-lite-v1:0

rejected: res-butter, res-heavy-cream, res-blueberries, res-raspberries
```

The deployed model read the sentence, proposed four resources, none was confirmed, and the case
sits waiting for a person. A reading that comes back inside its schema authorises exactly as much
as one that never arrives, which is nothing.

### 4.4 A restart, and no duplicated effect

`deploy.sh rollout` rebooted `i-087c742587f83d61d`. The host came back through the systemd unit,
converged from SSM, and served `87f3a13f26a9` again. The confirmed case read out identically
either side of the reboot: same headline, same case version, the same six per-promise outcomes,
and the same per-order effect counts with nothing above one.

### 4.5 A real certificate, according to the deployment rather than this laptop

This machine's antivirus intercepts TLS, so its view of the certificate proves nothing. The
host's own log does: five Let's Encrypt validation servers fetched the HTTP-01 challenge for
`184.194.40.87.sslip.io`, `validations succeeded; finalizing order`, and
`certificate obtained successfully  issuer=acme-v02.api.letsencrypt.org-directory`.

### 4.6 The stream, live, in a browser on the public name

`GET /events` answers `text/event-stream` to a session and `401` to nobody. With a stream held
open, a report posted from another connection produced `case.opened`,
`workflow.step.completed` and `exception.semantic_interpretation_requested` frames as they
happened. In the browser the page's own indicator reads `live`, and the committed browser test
proves that word is a state and not a constant: with `/events` refused at the network the case
still renders and the indicator refuses to say `live`.

### 4.7 A judge, in a browser, on the deployed name

`https://184.194.40.87.sslip.io/` serves the sign-in surface with one button. Pressing it lands
on a real case with `?case=<id>` in the address bar, the observer named in the header, the
conversation panel in its read-only posture, no confirmation control anywhere, and the untouched
proof reading *5 left alone of 6 this case considered, 0 incident-caused effects on them*. A deep
link to another case id loads that case directly.

### 4.8 Nothing secret is in what the browser receives

The served `index.html`, the hashed JavaScript bundle and the stylesheet were fetched and
searched for the deployment's actual secret values — the MCP bearer token and the seeded worker
password, read from SSM for this check — and for `postgres`, `supabase`, `AKIA`,
`rds.amazonaws`, `PP_SESSION`, `PP_INTERNAL`, `X-Service-Token`, `internal/intents` and any
private key header. Every one of them is absent. The eleven occurrences of the string `password`
are the sign-in form's field and label and React's own input-type table.

## 5. What this did not do

- **No IAM was created, changed or requested.** Every action used permissions the roles already
  held, and the registry-wide `ecr:DescribeRepositories` denial that a scoped role correctly
  returns was left exactly where it is.
- **Nothing outside this project was touched.** The account carries an unrelated `careloop`
  project; no action here named a resource that was not `promisepatch`, and the developer role
  cannot reach one that is not.
- **No new cost-bearing resource exists.** Same one `t4g.small`, same `db.t4g.micro`, same
  Elastic IP, same two ECR repositories, same log group. The replaced instances are terminated.
- **The worker password was never typed into a browser.** Worker sign-in is proved at the HTTP
  level, against the same endpoint the form posts to.
- **No measurement of anything is claimed**: no timing, no voice turn, no benchmark.
