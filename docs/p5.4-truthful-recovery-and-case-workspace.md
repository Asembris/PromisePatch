# P5.4 — truthful recovery, and the first case workspace

What was built, what was proved, and what is deliberately still absent. [P5.3](p5.3-conversational-orchestrator.md)
left the canonical case at `EXECUTING` with nothing carried out. This slice finishes that
sentence: the confirmed case runs through the recovery machinery that has existed since P3, and
what it produces is displayed to a person — for the first time — as a whole case rather than as
an order book.

Nothing here redesigns settled architecture. The engine, the step ledger, the outbox, the order
mirror, the approval protocol and the deterministic renderer are the ones that were already
there; what is new is one pure projection, one read API, one screen, and the proofs that carry
the canonical path through all of them. The rules being satisfied are in the
[P5 product contract](p5-product-contract.md).

## What a confirmed case actually does

One spoken exception, four tool calls over the real MCP transport, and four different endings —
each one produced by the machinery that owns it, and each one said in the word bound to it:

| promise | classification | ending | true because |
|---|---|---|---|
| Priya Nair, `EXT-A` | `AUTO_RECOVERABLE` | **RECOVERED** — "changed" | the External Order System's own event came back and the mirror moved |
| Tomas Lindqvist, `EXT-B` | `APPROVAL_REQUIRED` | **REQUESTED** — "asked" | the provider acknowledged delivery and stamped a `provider_ref` |
| Okafor-Reyes, `EXT-C`; Lena Fischer, `EXT-D` | `BLOCKED` | **ESCALATED** — "needs you" | no pre-authored variant exists; the track is on the owner's desk |
| Ahmed Bouazizi, `EXT-E`; Cafe Marlow, `EXT-F` | `UNAFFECTED` | **UNTOUCHED** — "left alone" | unreachable from the exception; **0 operational effects** |

The two `BLOCKED` promises do cause one thing: their production tasks are held, so the kitchen
stops work that is about to be wasted. That is an effect on a *threatened* promise and is
counted as one. The untouched pair cause no amendment, no message, no reservation change, no
production hold and no escalation, and the count published for this scenario is **0 of 2**.

## The three rules that are about words, not outcomes

Each of these is a claim the product could make one step too early, so each is proved by holding
the intervening state open and reading the case out loud in the middle of it.

**Recovered means observed.** Between the order system accepting the amendment and its event
coming back, the case is read over the real transport and says *"changing the order now"*. The
effect row is `DELIVERED` with a provider reference — the call really was accepted — and the
promise is `APPLYING`. `": changed"` appears nowhere until the echo has been ingested and the
mirror agrees.

**Asked means delivered.** The approval step is deferred so the message sits queued, and the
case is read again. The promise is not `REQUESTED`, the request carries no `provider_ref`, and
`": asked"` appears nowhere. Releasing the step and letting the dispatch complete is what makes
the word true.

**A refusal is not a success.** When the order system moves `EXT-A` on under its own authority
before the amendment lands, the amendment is refused, the promise escalates, and the word
"changed" is never said about it. The customer's newer order stands.

And the gate in front of all three: a planned case, drained through every worker cycle it will
offer *without* a confirmation, raises no effect at all and leaves the order system's book at
version 1. An `AUTO_RECOVERABLE` classification is a permission, and this is the test that says
so out loud.

## Band 2: the one thing that is yours

The workspace's second band needed a value nothing computed yet, so `status_view` gained one —
and it is a **pure projection**, under the same import contract as the rest of that module: no
database, no clock, no environment.

`CaseView.next_action` is exactly one `NextAction`, with an `ActionOwner` of `YOU`, `OWNER`,
`CUSTOMER`, `SYSTEM` or `NOBODY`. It is chosen by an ordered walk rather than a score, because
"what is mine?" has to have one answer: an open question first, then a reading a person owes,
then a plan awaiting a yes, then any promise on the owner's desk, then a customer's clock, then
the work being carried out, then nothing. An escalation outranks a customer deadline because a
customer's clock runs on its own and an owner's does not — **nothing at all happens to a blocked
promise until a person picks it up**, and that is the sentence the band says.

Every `PromiseState` also gains an owner and a next action, mapped exhaustively so a new state
is a mapping error rather than a promise that silently becomes nobody's. `DECLINED`, `STALE` and
`EXPIRED` belong to the owner for the same reason `ESCALATED` does: no automatic step follows
them.

The spoken `status` rendering is **unchanged**. Band 2 is a screen affordance in this slice, and
altering the sentences a worker hears over MCP was not part of finishing the recovery story.

## The read API

Two endpoints, both session-authenticated, both reads, and there will not be a write among them.
A worker changes a case by *saying* something, through the conversational surface, where the
attestation and the audit row are written together. A browser button that posted a state change
would be a second authority with none of that machinery around it.

| endpoint | answers |
|---|---|
| `GET /api/cases` | every case, newest first, with its state and the worker's opening sentence |
| `GET /api/cases/{case_id}` | the five bands of one case, plus the evidence behind them |

`intake.require_permitted` runs here exactly as it runs for the MCP surface — a case id is a
value a caller can type into a URL — and existence is checked before permission so "no such
case" and "not yours" stay different answers.

The response is built by `promisepatch.api.views.cases` from **one projection of one durable
read**: `analysis.read_case_status` → `status_view.project` → the bands. The operator CLI, the
MCP `status` tool and this screen therefore describe a case identically, because they are the
same two calls. Nothing is reworded on the way out; `phrase`, `sentence`, `reason`,
`next_action` and the band titles are copied.

## The workspace

Four bands and one drawer, in the contract's order, at `?case=<id>`.

1. **What happened** — the worker's own words, verbatim, with who attested them and when. An
   unresolved ambiguity appears here as the question with its options, never as a result.
2. **What you must do now** — exactly one action, with the person it belongs to.
3. **What changes, under whose authority** — threatened promises grouped by the backend into
   standing preference / customer / owner, each with its phrase, its state name, its reason, its
   deadline and its own next action.
4. **What was left alone** — the untouched promises, with the backend's count, present even when
   long. This band carries the product's central claim.
5. **Evidence** — collapsed. Case and track identifiers, rule ids, reason details, fingerprints,
   idempotency keys, provider references and the approval's own posture. It arrives with the
   case, so opening it issues no request — asserted in a test, because a drawer that fetched
   would be a drawer whose contents could disagree with the bands above it.

**The screen renders and does not decide.** Every sentence arrives composed; the counts arrive
counted; the grouping arrives grouped. A screen that wrote its own word for `RECOVERED` or
recounted the untouched promises would put the truthful vocabulary in a second place that nobody
tests against a durable case. Status is legible without colour: each row shows the phrase a
person reads *and* the state name, with tone as decoration on top.

**Reload and reconnect.** The case id lives in the address bar, not in a `useState`. There is no
client-side selection to lose, so a refresh, a restored tab or a pasted link mounts the app
already pointing at the same case and renders a fresh read of it. A feed frame invalidates the
open case as well as the order book, so a reconnecting browser cannot be left showing a plan the
case has already moved past.

## What was proved, and how

Two new backend suites, both against real PostgreSQL, plus one new frontend suite.

**`test_truthful_recovery.py` — 9 tests.** The conversation happens over the real MCP transport
(a real server, the official SDK client, an authenticated HTTP hop to the intent API); the
recoveries happen in a real worker process; the amendment is a real HTTP request the External
Order System parses; the echo is a real signed webhook PromisePatch verifies. Nothing inserts a
row and no domain command is called to move a case along — the only direct database access is
the reads that check what it all left behind.

- the confirmed case reaches all four outcomes, and the order system's own version has moved
- "changed" is not said before the echo; it is said after
- "asked" is not said before the provider's receipt; it is said after
- blocked promises stay an explicit owner action, raise no effect, and flag the case
- untouched promises carry zero incident-caused effects, and their held tasks are exactly none
- two independent connections read the same case identically
- a refused amendment escalates instead of claiming success
- nothing at all is carried out before the worker's yes
- a confirmation quoting a plan nobody offered leaves nothing to execute

**`test_case_workspace.py` — 13 tests.** The endpoint over the same real machinery: the bands,
the contract's authority order, the backend-published untouched count, the open question, the
four settled outcomes, a blocked promise's owner/reason/next action, an effect in flight that is
not shown as complete, the evidence drawer's identifiers, a reload returning the same answer, a
**second application process** (its own lifespan, own pool, own session) reading the same case
identically, and the list a browser with no address uses to find its way back.

**`caseWorkspace.test.tsx` — 18 tests.** The real client, the real query layer and the real
components against a stubbed `fetch`: the four bands, the four outcomes in the backend's own
words, an `APPLYING` promise that never reads as "changed", every blocked promise carrying an
owner, every row legible as text, a failed read reported as a failure to read rather than as a
case with nothing in it, the collapsed drawer and its no-extra-request rule, mounting at a case
address, a feed frame refetching the open case, and navigation in and out of the address bar.

Existing suites are unchanged and still pass. **No live model call: nothing in this slice
reaches a provider, and neither holdout was opened.**

## Limitations, stated

- **Band 2 is not spoken.** The MCP `status` rendering is unchanged, so a worker talking to the
  surface still hears the case without its single next action. Wiring band 2 into speech is a
  vocabulary change and belongs with the interaction work, not with the recovery work.
- **The evidence drawer is what `read_case_status` holds.** Snapshot fingerprints, rule ids,
  revalidation checks with their compared values, effects and approvals are all there; step
  ledger rows, the sender chain and audit rows are not, because that read service does not
  expose them and adding a second query would have been a second description of a case.
- **`explanations.render` is not yet wired to the workspace.** Its inputs are engine evidence
  built from a live snapshot, so reaching it from a durable case means re-running analysis —
  which is exactly the second implementation of a decision that `status_view` exists to avoid.
  The per-promise "why" on the screen is the durable reason, rule id and classification.
- **The owner is a role, not a person.** "The owner" is truthful and is what the fixture
  supports; naming an individual would need an assignment the domain does not record.
- **No browser end-to-end run.** The Playwright suite needs the whole Docker stack; the
  workspace is proved by the component suite and by the API suite against real PostgreSQL.
- **The published untouched figure remains 0/2 for this scenario only**, scoped by case, command
  and idempotency identity, exactly as the contract defines it. It is not a claim about a
  benchmark, and no scenario suite was run.

## Not in this slice

The bounded withdrawal — the fifth tool — is still **absent rather than stubbed**. Voice, the
Telegram channel, the AWS deployment and every P6 concern are untouched. P4.8 stays closed, both
holdouts stay sealed, and no benchmark program was started.
