# P7.3 — the implementation plan

**Local and uncommitted, on purpose.** This page is the frozen plan for the multi-session P7.3
migration. It is written before any implementation so the architectural decisions are made once,
in writing, against the code as it actually stands rather than against a memory of it. It is not
a record of work done: **nothing in this session changed code, touched AWS, deployed anything or
made a commit.**

It resolves the five blockers P7.1 left open or discovered, and it freezes eight implementation
sessions with their objectives, files, dependencies, tests, commit boundaries and exit criteria.

Nothing here reopens a closed gate, redesigns frozen architecture without saying so, or edits a
label. Where a decision departs from a frozen document, §11 names the departure and the ADR that
must carry it **before** the code lands.

## 2. The architecture decision: incremental refactor, not rewrite

**Decided: refactor the presentation layer in place. Do not rewrite the frontend.**

The reasoning is that the correctness layer and the presentation layer are already separate, and
only the second one is wrong for P7.

What is correct today and is **kept unchanged in structure**:

| layer | files | why it stays |
|---|---|---|
| Transport | [client.ts](../apps/frontend/src/api/client.ts) | Cookie credentials, CSRF header, `ApiError` carrying the backend's code. The session design depends on it. |
| Server state | [queries.ts](../apps/frontend/src/api/queries.ts), [queryClient.ts](../apps/frontend/src/app/queryClient.ts) | "Server state is the state; there is no client store." That is the truthfulness rule expressed as a data layer. |
| Freshness | [stream.ts](../apps/frontend/src/api/stream.ts), [useEventStream.ts](../apps/frontend/src/api/useEventStream.ts) | A real SSE feed whose only effect is *refetch the authoritative read*. It stores no frame payload and reconstructs no view, and it already models `resyncing` honestly. |
| Routing | [useCaseRoute.ts](../apps/frontend/src/app/useCaseRoute.ts) | The case id lives in the address bar, which is what makes reload, tab restore and a second process land on the same durable case. |
| Types | [types.ts](../apps/frontend/src/api/types.ts) | Mirrors the backend schema; extended, not replaced. |

A rewrite would have to reproduce all five, and the SSE hook in particular encodes a subtle
correctness property — a frame is a signal, never a source of state — that a rewrite is likely to
lose by making the stream a store.

What is genuinely wrong for P7 and **is replaced**:

- The band rendering in [CaseWorkspace.tsx](../apps/frontend/src/features/case/CaseWorkspace.tsx) —
  minimal, and designed before the P7.1 contract existed.
- [tones.ts](../apps/frontend/src/components/tones.ts) — decides tone by substring match on a state
  name, i.e. the screen deriving a meaning rather than being handed one. Replaced by an explicit,
  exhaustive mapping over the fourteen promise states.
- [primitives.tsx](../apps/frontend/src/components/primitives.tsx) — replaced by the twelve
  components of the design handoff.
- Engineering-console empty and error copy.
- [LiveOperations.tsx](../apps/frontend/src/features/live-ops/LiveOperations.tsx) — demoted from the
  landing surface to the secondary order book. Demoted, not deleted: it renders real reads.

**Refactor rule for every session below:** a presentation change may not alter a query key, a
fetch, a stream behaviour or a type's meaning in the same commit. If a presentation session finds
it needs a data change, that change is a separate commit; if it needs a *backend* change, it is
raised to session C rather than composed on the screen.

## 4. Blocker A — the judge entry

### Decision

**A server-issued, scoped, read-only observer session, minted by an unauthenticated
`POST /api/auth/demo-session`, backed by a real third worker role that the domain refuses every
write to.**

### How it works

1. **A new worker role, `observer`.** [db/types.py](../apps/backend/src/promisepatch/db/types.py)
   constrains `WORKER_ROLES` to `("baker", "owner")` with a CHECK constraint, so this is a migration
   plus one seeded worker row (`judge`) with an unusable password hash — it can never be reached by
   `POST /api/auth/login` at all.
2. **The domain gains one function and loses none.**
   [`intake.require_permitted`](../apps/backend/src/promisepatch/domain/intake.py) — "who may *speak*
   on a case: the worker who opened it, or an owner" — is **unchanged**, so an observer can never
   write, confirm, clarify, report or reach any governed path. A new
   `intake.require_readable(connection, case_id, worker_id)` admits the opener, an owner, **or an
   observer**, and is used by `GET /api/cases` and `GET /api/cases/{id}` only.
3. **Read-only is structural, not route discipline.** Because writes gate on the unchanged
   `require_permitted`, a write route added later with no observer check still refuses an observer.
   The capability is additive and read-only *by construction*. A route-level allowlist would fail
   open the first time somebody forgot it.
4. **The endpoint issues; it does not authenticate.** No credentials in, none published, and no
   field naming a worker. The server chooses the worker (the seeded `judge`), the id, the expiry and
   the CSRF token, exactly as login does.
5. **Bounded.** TTL **60 minutes** rather than the 12-hour worker `SESSION_TTL`; rate-limited per
   client with the existing `FixedWindowLimiter`; `Origin`-checked against `PP_CORS_ORIGINS` exactly
   as login is; and gated by a new setting `PP_DEMO_SESSION_ENABLED` that is **off by default**, so
   it is a deliberate deployment choice and not a standing anonymous-session endpoint in every copy
   of the repository.
6. **Revocable.** It is an ordinary session row, so `revoked_at` revokes it on the very next request
   and `pp reset-demo-state` already invalidates every session in the database.
7. **The screen is told, not left to infer.** `may_speak: false` arrives on the case response
   (§3 #6), so the conversation panel renders its read-only posture because the backend said so.

### Why not the alternatives

| rejected | why |
|---|---|
| Published read-only credentials on the sign-in screen | P7.1 allows it, but it is a standing credential in a public repository and in a video frame, it costs the judge typing, and it is strictly worse than an equivalent that needs neither. |
| A judge session as `maya` (baker) or as the owner | Owner impersonation with full write authority behind it — a judge could confirm a plan. Forbidden outright. |
| A session-level `scope` column on an ordinary worker session | The session would still *name* a real worker, so any leak of the scope check becomes an attributed write. The role-based answer makes the refusal the domain's. |
| No gate at all on reads | Removes `require_permitted` from the read path, which is the check P5.1–P5.4 deliberately share with the MCP surface. |

### The honest statement of what this changes

This **broadens read access** to a new principal kind. It is not a weakening of an existing check —
nothing admits anybody it did not admit before — but it is a deliberate, documented addition to the
domain's permission surface, and it is named as one here rather than slipped in as a route. It gets
its own tests (§8, session F) and it is the one blocker resolution worth the user's explicit
agreement before session F begins (§12).

## 5. Blocker B — frontend deployment

### Decision

**The backend image serves the built assets. No new service, no new image, no new IAM.**

### The arithmetic that decides it

Two hard constraints, both measured from the repository rather than assumed.

1. **The deployed compose file is 4052 bytes against a 4096-byte cap.**
   [docker-compose.deploy.yml](../deploy/compose/docker-compose.deploy.yml) is uploaded to an SSM
   standard-tier parameter and [deploy.sh](../deploy/deploy.sh) refuses the upload above 4096 bytes.
   **44 bytes of headroom.** A frontend service block is 250–350 bytes. It fits only by deleting the
   file's 919 bytes of explanation, which is the only place the deployed topology is explained.
2. **The instance role's ECR read is enumerated to exactly two repositories** —
   `promisepatch/backend` and `promisepatch/order-simulator` — in
   [the template](../deploy/cloudformation/promisepatch.yaml). A third image means editing an IAM
   policy. It would *not* need the account owner: the deployment role holds `iam:PutRolePolicy` on
   `PromisePatchInstanceRole`, and the developer role may `ecr:CreateRepository` on
   `repository/promisepatch/*`. It is possible. It is simply not free, and it is not necessary.

### The comparison

| option | new ECR repo | IAM movement | compose bytes | Caddyfile | judge reliability | update path |
|---|---|---|---|---|---|---|
| Dedicated frontend image + service | yes | one ARN added to the instance role | +250–350, **over cap** without deleting the file's explanation | +1 handle | one more container that can fail independently | a second build/push/tag |
| **Backend image serves assets** ✅ | no | **none** | **0** | net **smaller** — a 404 catch-all becomes a proxy | the UI is up exactly when the API is up, and Caddy already gates on `api` healthy | one image tag moves both |
| Caddy serving a mounted dist | yes, in practice | same as option 1 | ~+40 | +1 file_server | same as option 1 | the dist must reach the host, which means either a new image (= option 1) or S3 and new IAM |

### How it is built

- [Dockerfile.backend](../docker/Dockerfile.backend) gains a **node build stage** (`npm ci` +
  `npm run build` against `apps/frontend`) whose only output copied into the runtime image is
  `dist/`. Nothing from `node_modules` reaches the runtime layer.
- The API app mounts the bundle **last**, after every router, with an SPA fallback that serves
  `index.html` **only** for paths that are not `/api`, `/events`, `/internal`, `/healthz` or
  `/readyz`. An unknown `/api/...` path returns a JSON 404, never the SPA.
- Cache headers: hashed assets `immutable, max-age=31536000`; `index.html` `no-store`. A stale
  `index.html` pointing at a deleted hashed bundle is the one failure mode that makes a deployed
  judge entry show a blank page.
- [Dockerfile.frontend](../docker/Dockerfile.frontend) **stays** and is unchanged. Local development
  keeps the Vite dev server and its proxy, which is what HMR needs; that is the ordinary dev/prod
  split, not a divergence in runtime behaviour.

### The security consequence that comes with it, and its control

Today `handle /api*` is the Caddy allowlist and **`/internal/intents/*` is unreachable from the
public hostname** — it falls through to the 404 block. Replacing that block with a catch-all proxy
to the API would publish the internal intent API, whose only remaining control would be the service
token the `api` container already holds.

**Required, and tested:** the [Caddyfile](../deploy/compose/Caddyfile) keeps an explicit
`handle /internal* { respond 404 }` **before** the catch-all, and
[scripts/deployment_smoke.py](../scripts/deployment_smoke.py) gains a check asserting that
`POST https://<host>/internal/intents/report` returns **404** from outside. This is a named
precondition of session H, not a nice-to-have.

### The costs, stated

- A frontend release now requires a backend image build. Acceptable: `deploy.sh images` already
  builds and pushes both images in one stage.
- The API process serves static files. It is one static mount on a process that already serves
  every read the SPA makes.
- It departs from `ARCHITECTURE_PLAN.md`'s "static SPA on S3 + CloudFront". P6.1 already departed
  from the same section's ECS/ALB/CloudFront compute topology, with reasons
  ([p6.1](p6.1-deployment-preflight.md)). §11 requires **ADR-0012** to record this one before the
  code lands.

## 6. Blocker C — the causal-chain and untouched-proof contract

### What already exists

`track_paths` stores, per track, **the traversed path in order**: `nodes` (JSONB, a list of
`PathStep` — `node_ref`, `edge_kind`, `role`, see
[propagation.py](../packages/promise-graph/src/promise_graph/propagation.py)), plus `role`,
`quantification` (`need` / `available_before_start` / `shortfall`) and `rule_id`.
`read_case_status` reads it today **only as a count**
([analysis.py](../apps/backend/src/promisepatch/domain/analysis.py)).

So the chain is durable, ordered and already committed. P7.3 projects it; it does not compute it.

### The contract

```
CausalStepView:
    slot:      "SHORTFALL" | "RESOURCE" | "VERSION" | "PROMISE"
    label:     str          # rendered by the domain
    detail:    str | None   # e.g. "needed 4.0 kg, 1.2 kg available, 2.8 kg short"
    node_ref:  str          # drawer vocabulary; never rendered in bands 1-4

CausalChainView:
    present:        bool
    steps:          tuple[CausalStepView, ...]   # ordered; empty when present is false
    absence_reason: str | None                   # the sentence for "no path reaches this promise"
    path_count:     int                          # how many paths this track has
    deciding_rule:  str | None                   # the rule_id of the path shown
```

`causal_chain: CausalChainView` is carried on **every** `PromiseWorkspaceView` — threatened and
untouched alike.

### The four requirements, and how each is met

| requirement | how |
|---|---|
| **Ordered path per threatened promise** | `steps` is emitted in `track_paths` order. The client renders the array as given and never sorts, filters or reverses it. |
| **N > 1 promises per authority lane** | The chain hangs off the **promise**, not the lane: `AuthorityBandView.promises[*].causal_chain`. Three promises in one lane is three chains, with no aggregation, no shared node and no merged trunk. A lane is a grouping of rows; the causal column is a property of a row. |
| **Untouched / no-path explanation** | `present: false`, `steps: ()`, and `absence_reason` carrying the domain's sentence for why nothing reaches it — which for `S11`'s `EXT-D` is Lena's own external edit, and for `EXT-E` / `EXT-F` is that the recipe reserves other resources. Band 4 states the reason rather than being silent, and the empty causal column is itself the selectivity claim. |
| **No client-side authority, count or causal recomputation** | Every label, detail, slot and sentence is the backend's. The client holds no `node_ref` → label map, no role vocabulary, no quantity formatter and no path arithmetic. `path_count`, `untouched_count`, `threatened_count` and `untouched_effect_count` are all backend integers. |

### The multi-path rule

A track with several paths returns **the deciding one** — the path whose `rule_id` equals the
track's `rule_id`, lowest `ordinal` as tiebreak — plus `path_count`, so the drawer can say "3 paths;
this is the one that decided it". **A merged or synthesised path is never returned**, because a
chain a judge reads as one traversal must be one traversal that actually happened.

### Fixed geometry

The four slots are the design handoff's fixed columns: *what did not arrive → what it fell short of
→ the version the order pins → the promise*. Every row occupies the same four positions whether its
chain is long or short, so a judge compares rows rather than relearning a layout. No node dragging,
no zoom, no physics, and no layout that differs between two loads of the same case.

## 7. Blockers D and E — voice scope and the conversation route

### E — the browser conversation transport

**Decision: three new session-authenticated routes on the API that call the same domain services
with a server-derived actor. The browser never touches `/internal/intents` and never holds the
service token.**

```
POST /api/conversation/report    -> intake.open_physical_exception
POST /api/conversation/clarify   -> intake.answer_clarification
POST /api/conversation/confirm   -> recovery.confirm_plan
GET  /api/cases/{id}             -> status  (already exists; gains `speech`, §3 #5)
```

| property | how it is enforced |
|---|---|
| **Session auth** | `PrincipalDep` — the same signed, `HttpOnly`, server-side session row the workspace reads use. |
| **CSRF** | `CsrfPrincipalDep`. These are the first browser mutations in the product, so the session-backed double-submit check in [dependencies.py](../apps/backend/src/promisepatch/api/dependencies.py) is load-bearing here for the first time. |
| **Actor server-derived only** | `worker_id = principal.worker_id`. The request models are `extra="forbid"` and **have no actor field**, so there is nothing for a caller to set — the same construction [intents.py](../apps/backend/src/promisepatch/api/routers/intents.py) uses, with the session as the source instead of `PP_SURFACE_WORKER_ID`. |
| **Clock server-derived only** | Read in the route, never accepted from the body. A caller that could set it could backdate a physical claim. |
| **Same `require_permitted` semantics** | Not re-checked in the route: the domain services call it themselves, exactly as they do for the CLI and the intent API. An observer session is refused *by the domain*. |
| **No duplicated domain logic** | The routes store and enqueue; they interpret nothing. The exception → `ApiError` mapping (`COMMAND_CONFLICT`, `PLAN_SUPERSEDED`, `NOT_AWAITING_CLARIFICATION`, `CASE_NOT_PERMITTED`, …) is **extracted from the intents router into one shared module** used by both, so the two transports cannot drift into different answers for the same refusal. |
| **`confirm` binds to a plan** | `plan_id` is required and compared under the confirming lock, exactly as [ADR-0010](adr/0010-plan-bound-worker-confirmation.md) fixes. A yes authorises the plan that was rendered and nothing else. |
| **No internal service flow exposed** | The service token is never sent to a browser, `/internal*` is 404ed at Caddy (§5), and a test asserts the conversation routes reject a request carrying only `X-Service-Token`. |
| **Permitted verbs come from the server** | The panel offers a verb only when the case's phase permits it, using the same closed mapping [orchestrator/policy.py](../apps/backend/src/promisepatch/orchestrator/policy.py) computes — surfaced through the case response rather than reimplemented in TypeScript. The domain checks every call again regardless of what was shown. |

**No model is in the browser path.** The orchestrator's `select_tool` chooses a verb when a
*conversation* drives itself ([ADR-0011](adr/0011-conversational-orchestrator-authority.md)); a
person pressing a button has already chosen. The panel calls the verb the person chose, and the
authority boundary is unchanged either way.

### D — voice scope, locked

**In P7.3, and no more than this:**

- **Push-to-talk**, held or toggled, in the conversation panel. Large, keyboard-operable, with a
  visible state at all times. **No wake word, no always-listening, and no claim of either.**
- **Labelled an Alexa+ simulation** that really calls the deployed loop — openly, as the official
  alternative path. Never presented as a native Alexa integration or a verified Echo deployment.
- **Transcript review before send, always.** Capture → transcript shown → editable → discardable →
  only then sent. A voice surface that acts on a misheard sentence has produced an attestation
  nobody made.
- **The same browser transport as typed turns** (§E above). One code path; voice sets the text of a
  turn and nothing else.
- **The same authoritative backend path**: same routes, same server-derived actor, same
  `require_permitted`, same `plan_id` binding, same `status_view` rendering.
- **The spoken reply is the backend's string, read aloud unchanged.** No client-composed sentence,
  no re-wording, no summary. Silence is better than a paraphrase of "planned".
- **All nine P7.1 §7 voice states** get a visible treatment; text is the equal path, never a
  degraded mode.
- Capture uses the browser's own speech recognition where available; **the text field is the
  fallback and is the same control**, so the panel works identically with no microphone at all.

**Explicitly not in P7.3:** Amazon Transcribe or Polly integration, a real Alexa skill, a wake-word
engine, barge-in DSP, any generic chatbot behaviour, and **the G7 ten-turn measurement itself**.
P7.3 builds the surface and the timing instrumentation. The predeclared ten turns, their recorded
timings and the published K/10 are a later slice, and **no turn has been recorded and no timing
exists** until it runs. Nothing in P7.3 may state or imply otherwise.

## 9. Tests, visual acceptance and rollback

### Visual acceptance

The [design handoff](p7.1-design-handoff.md)'s §9 list is the acceptance list and is not restated.
Two additions specific to implementation:

- **Every number, sentence, count and state name on any screen traces to a named backend field.**
  Session I walks the rendered surface field by field. A value with no field is a defect, and the
  fix is a backend field, never a screen computation.
- **The five demo-critical frames are captured as screenshots from the real stack** and checked
  against the contract's descriptions — in particular frame 3, `PLANNED` in full with no completion
  mark anywhere.

### Rollback

- **Per session.** Each session is a small ordered set of commits behind a green gate. A session is
  reverted by reverting its commits; no session leaves the tree in a state where the previous
  session's tests fail.
- **Backend fields (session C).** Additive only. Nothing is removed or renamed, so a reverted
  frontend session still reads a valid response.
- **Deployment (session H).** The rollback is a **previous image tag**: `deploy.sh` tags images with
  the commit SHA and the stack takes the tag as a parameter, so reverting the deployed SPA is a
  stack update to the prior tag, and the Caddyfile change is a one-parameter SSM re-upload.
- **The judge session (session F).** `PP_DEMO_SESSION_ENABLED=false` removes the endpoint without a
  code deploy, and `revoked_at` kills an issued session immediately.

## 10. NON-GO rules

These are refusals, not preferences. Each one is checked in session I.

1. **No full frontend rewrite.** The transport, query, stream, routing and type layers are refactored
   in place or not at all (§2).
2. **No replacement of the API / query / SSE layer without a reproduced need.** A behaviour nobody
   has reproduced is not a reason to replace a layer that encodes a correctness property.
3. **No client authority decision.** The screen never decides what may happen, who may act, what a
   state means, or whether a group exists. It renders what it is given.
4. **No fabricated count, path, state or sentence.** Every one is a backend field. A missing field is
   a backend task.
5. **No optimistic external effect.** Nothing changes on screen until the backend says it did. No
   pre-applied tick, no local state, no anticipatory row, no progress bar for work not started.
6. **No prototype runtime copied into production.** `handoff/` contributes visual language only.
   Not a component, not a hook, not a state machine, not a fixture, not a file.
7. **None of the prototype's scaffolding ships**: no `devStage`, no frame rails, no P7.3 badge, no
   fixture control, no stage switcher, no demo-mode toggle, no seeded sample data on screen.
8. **No disabled control for a capability that does not exist.** The bounded withdrawal and
   physical-fact correction are absent, and absent is how they are drawn: not at all.
9. **No dashboard.** No KPI tile, chart, trend, sparkline, activity feed, filter bar or global
   navigation.
