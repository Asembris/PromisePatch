# P5.2 — clarification and plan confirmation over MCP

What was built, what was proved, and what is deliberately not here yet. This slice takes the
[transport spine](p5.1-mcp-transport-spine.md) from two tools to four, so the canonical
conversation runs end to end: a worker reports, the system asks a consequential question, the
worker answers it, a plan is offered, and the worker explicitly authorises **that** plan.

The decisions are recorded in [ADR-0010](adr/0010-plan-bound-worker-confirmation.md). The rules
they exist to satisfy are in the [P5 product contract](p5-product-contract.md).

## The tool surface, now four

`report`, `clarify`, `confirm`, `status`. The bounded withdrawal is still **absent rather than
stubbed**: a tool that exists and refuses is a different thing from a tool that does not exist.

Everything P5.1 established is unchanged and re-asserted: `mcp==2.2.0`, protocol revision
**2025-11-25** through `initialize`, stateless Streamable HTTP at `POST /mcp`, the bearer check
outside JSON-RPC, `Origin` 403 / `Host` 421, a correlation id per call reaching the governed
audit row, and no tool argument anywhere in the chain carrying an actor or a clock.

### `clarify`

| | |
|---|---|
| arguments | `case_id`, `answer` (verbatim), `client_request_id` (optional idempotency key) |
| result | `{ok, intent, correlation_id, case_id, state, warnings, statement_id, created, attested_by, speech}` |
| durable effect | one `case_reports` row of kind `CLARIFICATION_ANSWER` holding the answer byte for byte, the open `exception_clarifications` row closed against it, one `BEGIN_INTERPRETATION` step, one `CLARIFICATION_ANSWERED` audit row |
| refusals | `INVALID_ARGUMENT` (nothing said, or a case id that is not one), `UNKNOWN_RESOURCE` (no such case), `UNAUTHORIZED_SURFACE` (not this surface's case), `CASE_NOT_IN_STATE` (not waiting for an answer; or a command id reused for different words), `ENGINE_UNAVAILABLE` |

The answer is forwarded untouched — not trimmed, normalised or case-folded — and the case is
still `CLARIFYING` when the tool returns. **Which physical outcome the answer selects is decided
by the worker process**, against the options captured from the delivery's own rows when the
question was asked, so an answer can only ever choose among outcomes that were already
possible. `created: false` is a success: this exact answer was already accepted.

There is no field for *which* question is being answered. A case has at most one open — a
partial unique index enforces it — and choosing among several would be an authority.

### `confirm`

| | |
|---|---|
| arguments | `case_id`, `plan_id` (**required**, from `status`), `client_request_id` (optional) |
| result | `{ok, intent, correlation_id, case_id, state, warnings, created, confirmed_by, applying, awaiting_approval, escalated, speech}` |
| durable effect | the case at `EXECUTING`, every blocked track escalated with its production tasks held, one `APPLY_RECOVERY` step per automatically recoverable track, one `REQUEST_APPROVAL` step per track whose customer must be asked, the `CONFIRM_PLAN` step row, and a `PLAN_CONFIRMED` audit row under authority `HUMAN_APPROVAL` |
| refusals | `INVALID_ARGUMENT` (blank plan, or a case id that is not one), `UNKNOWN_RESOURCE`, `UNAUTHORIZED_SURFACE`, `CASE_NOT_IN_STATE` (not `PLANNED`; superseded plan; command id reused for a different plan), `ENGINE_UNAVAILABLE` |

**No network call and no outbound effect.** Every count in the result is a permission or a
queued intention, and there is no field in the result that could say an order was changed.
`awaiting_approval` authorises *asking* a customer and nothing further.

There is no `confirmed: bool`. A false one would be a withdrawal wearing a confirmation's name;
calling the tool *is* the yes.

### `status`, extended

Two fields, both so that a surface never invents what it should be delivering:

- **`question`** — the open clarification with the answers it will accept, present only while
  one is open, and rendered into `speech` as the question itself. A surface told only "waiting
  for your answer" has to reconstruct what was asked, and the only material it has is the
  original sentence.
- **`plan_id`** and **`awaiting_confirmation`** — present **only** on a `PLANNED` case. Handing
  an identity over on any other state would invite a confirmation of something nobody is being
  asked about: the domain would refuse it, and the conversation would have been wrong out loud
  first.

## Authority and binding

**A confirmation is bound to a plan, not to a case.** `plan_id` is a SHA-256 digest over the
case id, the case version and every track — untouched ones included — reduced to what band 3 of
the workspace shows: state, classification, chosen option, the version that option would write,
and the fingerprint planning watches. It is:

- **derived, never stored** — recomputed from the rows on every read, so a mismatch means the
  rows moved rather than that a cache went stale;
- **checked under the lock** the confirmation is written with, by
  `recovery.current_plan_id`, against `analysis.read_case_status`'s value — two producers, one
  shape, and [a test drives both and asserts they agree](#what-was-proved-and-how);
- **opaque** — 64 hex characters that name a plan the server rendered and cannot describe one
  it did not. There is no tool argument naming a track, an option, an order or a recipe
  version, so a confirmation cannot be *assembled*, only quoted back;
- **fail-closed on any committed change to the case**, because the case version is in the
  digest. Re-reading the status is one turn; a yes to something nobody saw is not recoverable.

**The transport cannot mint one.** `promisepatch.mcp` still cannot import the domain, the
database, the API package or SQLAlchemy — it has no rows, so it forwards the string it was
given and computes nothing.

**Worker confirmation is not customer consent.** Different people, different authorities,
recorded separately, and never rendered in the same words. The server's own `instructions` say
so to the model, and no endpoint in this chain can record a decision on a customer's behalf.
Consent remains a literal `YES`/option code/`NO` arriving on that order's own channel.

**The identity of who is speaking is unchanged.** The attesting worker comes from the intent
API's `PP_SURFACE_WORKER_ID`. A tool call naming a worker or an `on_behalf_of` is naming a
value the server ignores; the forwarded request carries exactly `{command_id, case_id, text}`
or `{command_id, case_id, plan_id}` and nothing else.

## Refusal, replay and staleness

| situation | what happens |
|---|---|
| answering a case that asked nothing | `409 NOT_AWAITING_CLARIFICATION` → `CASE_NOT_IN_STATE`. No report row is written. |
| answering somebody else's case | `403 CASE_NOT_PERMITTED` → `UNAUTHORIZED_SURFACE` |
| the same answer delivered twice under one key | one row, `created: false`, which is a success |
| one command id, two different answers | `409 COMMAND_CONFLICT` → `CASE_NOT_IN_STATE` |
| confirming before a plan exists | `409 PLAN_NOT_CONFIRMABLE`; the case stays where it was |
| confirming a plan the case never offered | `409 PLAN_SUPERSEDED`; the case stays `PLANNED` |
| confirming a plan that was re-made after it was read | the same, and the remedy is one turn: read `status`, tell the worker what changed, ask again |
| the same confirmation delivered twice under one key | confirmed once, `created: false`, and the speech says so rather than claiming a second one |
| one command id, two different plans | `409 COMMAND_CONFLICT` — two requests claiming one identity |
| confirming an already-confirmed case under a new key | `409 PLAN_NOT_CONFIRMABLE`: the case has left `PLANNED` |

Every 409 above reaches the model as `CASE_NOT_IN_STATE`, one of the frozen five from the
architecture's MCP section, with the engine's own wording withheld. The remedy is the same for
all of them — read `status` again — so a sixth code would buy the conversation nothing.

## The truthful vocabulary, extended without new claims

Both new tools return a `speech` rendered by `promisepatch.domain.status_view` and delivered as
given, rather than composed in the transport. Confirmation is precisely where language outruns
reality, so the sentence that reports it lives beside the table that says `AUTHORIZED` is a
permission and `RECOVERED` is an observation, and is covered by that module's purity contract.

- An answer receipt promises nothing: *"Got it, and I have written that down exactly as you
  said it. Nothing has changed yet."*
- A confirmation reports permissions and closes on the fact that nothing is done: *"Confirmed:
  1 order covered by a standing preference, 1 order where I still have to ask the customer and
  1 order that need the owner. Nothing has been changed yet — ask me for the status to hear
  what actually happened."*
- `status` immediately after a confirmation reports `AUTHORIZED`, never `REQUESTED` and never
  `RECOVERED`, and the untouched count is unchanged by the yes.

## What was proved, and how

`apps/backend/tests/test_mcp_protocol.py` — **74 tests, offline**: no database, no credential,
no model, no network beyond a loopback socket, driving the real server with the official SDK
client. Everything P5.1 proved is still asserted; new in this slice:

| area | what is checked |
|---|---|
| discovery | exactly `clarify`, `confirm`, `report`, `status`; the withdrawal is still absent |
| `confirm`'s schema | exactly `{case_id, plan_id, client_request_id}`, with `case_id` and `plan_id` required — nothing that could describe a plan instead of quoting one |
| forwarding | the answer arrives byte for byte; the plan identity arrives as given; the service token and correlation id are on the wire |
| identity | an argument naming a worker or an `on_behalf_of` changes nothing, and the forwarded body carries exactly three fields |
| idempotency | one `client_request_id` reaches one command for `clarify` too |
| invalid calls | a blank answer, a missing `plan_id`, a blank `plan_id`, a case id that is not one — all refused before the engine is troubled |
| refusal mapping | `NOT_AWAITING_CLARIFICATION`, `PLAN_SUPERSEDED` and `CASE_NOT_PERMITTED` become the frozen codes, with the engine's own code withheld from the text |
| completion language | `confirm`'s result has no field that could report an outcome, and its speech says nothing has been changed |
| `status` | the question and its options are delivered as the engine reported them; a planned case hands back an identity; a clarifying one hands back none |
| instructions | the four boundary sentences reach the model: cannot confirm on a worker's behalf, cannot confirm a plan it has not read, worker confirmation is not customer consent, cannot choose who is speaking |

`apps/backend/tests/test_plan_identity.py` — **13 tests, pure**: the same plan read twice is one
identity whatever order the rows came back in; a re-planned track, a changed authority, a
different chosen option, a moved fingerprint, a promise joining the untouched band and any case
version bump each produce a different one; two cases holding identical plans are not one plan;
and the value is opaque, fixed-width and carries nothing it was made of.

`apps/backend/tests/test_status_view.py` — **31 tests, pure**: P5.1's vocabulary rules,
plus the question read out with its options, the plan identity present only while a plan is
offered (parametrised across six other case states), and the confirmation sentence asserted
against the words it may **not** contain.

`apps/backend/tests/test_intent_api.py` — **43 tests, PostgreSQL**: what a call *causes*. The
intent API directly for `clarify` (verbatim storage, attribution, the not-asking refusal,
permission, redelivery, conflict) and `confirm` (authorises and completes nothing, before a
plan, another case's plan identity, a genuinely re-planned case, redelivery, replay under a
different plan, double confirmation, permission, no credential), the two-producers agreement
test, and then the whole chain end to end on two real sockets:

- **the canonical conversation over the real protocol** — `report` → the case asks a question →
  `status` returns it → `clarify` answers it → `status` offers a plan and an identity →
  `confirm` authorises it → `status` shows authorised and *nothing carried out*, with the
  untouched count unchanged. Nothing is inserted into the database by the test and no domain
  service is called directly; the worker process runs between the turns exactly as in the
  product, and the durable rows are asserted afterwards over a separate connection.
- **a stale plan confirmed over the transport** — refused as `CASE_NOT_IN_STATE`, the case
  still `PLANNED`, and then the re-read plan confirmed successfully in one more turn.
- **answering a case that asked nothing**, over the transport, leaving one report row.
- **a confirmation surviving the connection that gave it** — authority is a row.

Also run: `ruff check`, `ruff format --check`, `mypy` (228 files), `lint-imports` (**26**
contracts kept, 0 broken — the new one is *a plan identity is derived from its arguments
alone*), and the recovery, revalidation, amendment and CLI suites that share the confirmation
path.

**No live model call was made and none was needed.** Nothing in this slice reaches a provider:
`clarify` stores words and `confirm` compares a digest. G5 item 9's bounded live conversational
smoke still belongs to the slice that adds the orchestrator.

## Limitations, stated

- **Staleness and "not planned" are one code to the model.** Both are `CASE_NOT_IN_STATE`, by
  the frozen-vocabulary decision in ADR-0010 §5. The intent API distinguishes them
  (`PLAN_SUPERSEDED` / `PLAN_NOT_CONFIRMABLE`) and an operator reading a log can tell them
  apart; a conversation cannot, and its remedy is the same either way.
- **A confirmation fails closed on any case change, not only a plan change.** The case version
  is in the digest, so an unrelated committed change to the case row refuses a confirmation
  that would otherwise have been fine. That is deliberate and is the cheap side of the trade;
  ADR-0010's revisit trigger names the fix if it turns out to fire in normal use.
- **`clarify` cannot address a specific question.** Correct while a case can only ever have one
  open, and something to revisit if that ever stops being true.
- **The two-clarification ceiling is the engine's, not the tool's.** A third question is not
  asked because the interpreter escalates instead; nothing in this slice enforces it at the
  transport, and nothing needs to.
- **No orchestrator.** Something still has to decide *which* tool to call. That is the next
  slice, and until it exists the tools are driven by a client rather than by a model.
- **`status` is still bounded.** The evidence drawer (band 5 of the case workspace) is not in
  the payload.
- Both holdouts remain sealed. P4.8 stays closed.

## Not in this slice

The conversational orchestrator, the bounded withdrawal (the fifth tool), voice, Telegram, the
Alexa+ simulation, the case workspace UI, and any cloud deployment.
