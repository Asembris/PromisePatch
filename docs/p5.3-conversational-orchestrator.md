# P5.3 — the truthful conversational orchestrator

What was built, what was proved, what one live conversation cost, and what is deliberately not
here yet. This slice puts a model into the loop over the four-tool surface
[P5.2](p5.2-mcp-clarification-and-confirmation.md) finished, so a worker can carry the canonical
interaction by talking — and it does so without giving the model any authority it did not have
when it was outside the loop.

The decisions are recorded in [ADR-0011](adr/0011-conversational-orchestrator-authority.md). The
rules they exist to satisfy are in the [P5 product contract](p5-product-contract.md).

## The orchestrator contract, in one page

`promisepatch.orchestrator` is a **client** of the MCP surface. It connects over the real
Streamable HTTP transport with a bearer credential, exactly as a third-party client would, and
an import-linter contract forbids it the domain, the database, the API package, the engine,
SQLAlchemy, an AWS SDK and the MCP server's own internals. Everything it can cause is something
an unrelated client could already cause.

One turn is: **choose → check → call at most twice → say what is true.**

| step | who decides | what it may be |
|---|---|---|
| the phase | deterministic code, from a `status` reading the server rendered | one of seven closed labels |
| the offer | a fixed table, phase → verbs | `REPORT` / `CLARIFY` / `CONFIRM` / `STATUS`, and `NONE` always |
| the verb | **the model**, one bounded semantic call | a member of the offer, or `NONE` |
| the arguments | deterministic code | the worker's turn verbatim, or an identity a tool returned |
| the yes | **the worker**, in their own words | a closed set of affirmations, no qualifiers |
| the words | `promisepatch.domain.status_view`, on the far side of two hops | delivered unchanged |
| the glue | **the model**, optional, ≤25 words | no digits, no outcome words, dropped unless the turn acted |

Everything in that table that is not marked **the model** or **the worker** is a function of
its arguments, in `promisepatch.orchestrator.policy`, under an import contract that forbids it a
clock, a socket, a client and a provider.

## The model authority boundary

**The model's only output is a verb.** The one new semantic job is `select_tool`, and its result
type is:

```python
class ToolSelection(Strict):
    tool: ConversationTool
    preface: str | None = Field(default=None, max_length=200)
```

There is no `case_id`, no `plan_id`, no `text`, no `answer`, no worker and no customer. This is
structural rather than validated: a fabricated plan identity is refused because the field it
would arrive in does not exist, and `extra="forbid"` rejects the answer rather than ignoring the
surprise. Everything that reaches a tool is filled in afterwards, from the worker's own turn or
from what `status` returned.

What the model is shown is equally small: the phase as one closed label, the verbs on offer, and
the worker's turn last and fenced as untrusted. **No case id, no correlation id, no plan, no
promise, no customer** — asserted, because a detail sent is a detail that can be repeated back as
though the model had established it.

| the model may | the model may not |
|---|---|
| read one worker turn | name a case, a plan, an order, a recipe version or a person |
| choose one verb from the offer | choose a verb the phase does not permit — refused at the boundary |
| choose `NONE` | supply any argument to any tool |
| write ≤25 words of glue | say what has happened, will happen, or is now true |
| — | confirm a plan; a yes is the worker's, checked separately |
| — | cause a second effecting call, or any retry |

### The three gates a confirmation passes

A `CONFIRM` needs all of them and they are independent:

1. **The phase permits it** — the case is `PLANNED` *and* handed over a plan identity. Computed
   from the server's own rendering.
2. **The conversation holds that identity** — read from `status`, quoted back opaquely. It
   cannot be described, only quoted, and the transport cannot mint one.
3. **The worker said yes** — every word of their turn, in order, is spanned by a closed set of
   affirmations and nothing else. `reads_as_worker_confirmation` is deliberately stricter than
   the domain, which treats the call itself as the yes. *(As shipped in P5.3 this was an opening
   affirmation plus a blacklist of disqualifying words; that rule was narrowed to the whole-turn
   allowlist on 2026-09-17 — see ADR-0015, "The rule, exactly". The gate's place in the argument
   is unchanged and the narrowing only refuses more.)*

Gate 3 is not the consent parser and shares nothing with it. Worker plan confirmation and
customer consent are different authorities; the orchestrator cannot import
`promisepatch.domain.consent`.

### The glue gate

A preface is refused — failing the **whole** answer, not trimmed — if it runs over 25 words,
contains a digit, or contains any of 39 words that report an outcome (`changed`, `sent`,
`asked`, `confirmed`, `done`, `sorted`, `recovered`, `safe`, …). It is delivered **only when the
turn did what was chosen**: a blocked or refused turn drops it entirely.

Stated as a floor, not a proof. It compares words against a list and understands nothing, and a
model determined to imply completion without any of them can. What it establishes is that the
sentence a worker acts on never comes from the glue at all — every authoritative word in every
reply was rendered by `status_view` from durable rows.

## Phase and tool policy

| phase | reached when | offers |
|---|---|---|
| `NO_CASE` | nothing reported yet | `REPORT` |
| `UNDERSTANDING` | headline `UNDERSTANDING` or `ANALYSED`; **or** any headline whose evidence is missing | `STATUS` |
| `CLARIFYING` | headline `CLARIFYING` **and** a question was handed over | `CLARIFY`, `STATUS` |
| `PLANNED` | headline `PLANNED` **and** `awaiting_confirmation` **and** a plan identity | `CONFIRM`, `STATUS` |
| `WORKING` | headline `WORKING` or `WAITING` | `STATUS` |
| `NEEDS_HUMAN` | headline `NEEDS_HUMAN` | `STATUS` |
| `SETTLED` | headline `SETTLED` or `CANCELLED` | `STATUS` |

Fail-closed in both conditional rows and in the default: a headline nobody has written yet, a
`PLANNED` case with no identity, a `CLARIFYING` case with no question all land on
`UNDERSTANDING`, whose only verb is a read. The failure mode of every gap in this table is a
conversation that can look and not touch.

**Availability is defence in depth and is described as such.** The offer is checked twice — by
the semantic boundary against the request, and by the policy before a call is built — and
neither is the real control. The domain checks every one of these again and refuses a call the
case cannot accept whatever this table believed.

### The budget

**Two tool calls per turn, at most one of which may affect state.** The second is always
`status`: it refreshes the phase for the next turn, and its rendering is read out only when the
case has arrived somewhere that wants the worker — a question to answer, or a plan to say yes
to. `STATUS` is the only verb that is not an effect, which is what makes spending the second
call on the truth safe.

**Nothing is retried.** A refusal is an answer: the loop says the deterministic sentence for its
code and gives the worker their turn back. The one corrective retry in the system stays where it
already was — inside the semantic gateway, spent on a schema, bounded at one. There is no retry
loop in the orchestrator and nothing that blocks waiting for a different result.

### What a failing turn says

Deterministic sentences, written in `policy` and never by a model: five for the orchestrator's
own refusals (`NOT_UNDERSTOOD`, `NOT_PERMITTED_HERE`, `NO_CASE_YET`, `NO_PLAN_TO_CONFIRM`,
`NEEDS_THE_WORKERS_YES`) and one for each of the six frozen `ToolCode`s. When a case is open,
the turn additionally reads it once and delivers that rendering, so a worker who was refused is
still told where things stand.

## The canonical conversation

Six turns, driven end to end over the real Streamable HTTP endpoint against the real server, the
real intent API and PostgreSQL. Nothing is inserted by the test and no domain service is called
to move it along; the worker process runs between the turns exactly as in the product.

| # | the worker says | verb | tools called | after |
|---|---|---|---|---|
| 1 | *today's raspberry delivery didn't arrive* | `REPORT` | `report`, `status` | case open, `UNDERSTANDING` |
| 2 | *what do you need from me?* | `STATUS` | `status` | `CLARIFYING`, the engine's own question read out |
| 3 | *just raspberries - the strawberries came* | `CLARIFY` | `clarify`, `status` | answer stored byte for byte |
| 4 | *so what's the plan then?* | `STATUS` | `status` | `PLANNED`, plan identity held |
| 5 | *yes, go ahead* | `CONFIRM` | `confirm`, `status` | `EXECUTING` — authorised, nothing done |
| 6 | *where does that leave us?* | `STATUS` | `status` | authorised, and said as such |

Asserted afterwards over a separate connection: exactly two `case_reports` rows holding the
worker's own words, both attributed to the server-configured worker, and a case at `EXECUTING`.
Asserted in the replies: no promise is ever rendered as `changed` or `asked`, the confirmation
says *"Nothing has been changed yet"*, and the untouched band is present and counted.

## Adversarial proofs

All offline, no model call, no network beyond a loopback socket.

| the attack | what happens |
|---|---|
| the model selects a verb this phase does not permit | refused by the semantic boundary as `UNSUPPORTED_VOCABULARY`, twice; **no tool is called**; the turn falls back to a read |
| the model returns a fabricated `plan_id` (or `case_id`, `text`, `answer`, `on_behalf_of`) | refused by the schema — the field does not exist. Five shapes, parametrised |
| the model tries to confirm without the worker | `CONFIRM` on *"that plan looks right to me"* → `NEEDS_THE_WORKERS_YES`; `confirm` is never called; the glue is dropped |
| a confirmation with no plan ever read | `NO_PLAN_TO_CONFIRM`, before the surface is touched |
| the provider is unreachable / times out | no verb, no effecting call, a deterministic sentence, one read |
| the tool surface is unreachable | `ENGINE_UNAVAILABLE`, "nothing has changed", and **no phase is invented** |
| the case moved between the decision and the call | `CASE_NOT_IN_STATE` → "that case has moved on"; the conversation ends holding the plan that is actually on offer, and no yes was recorded — proved **over the real transport** with a genuinely re-planned case |
| the model writes glue claiming the order is changed | the whole answer is refused as `UNSUPPORTED_CLAIM`, twice; the claim appears nowhere in the reply; the worker hears the deterministic sentence and the true status |
| a turn longer than a semantic request can carry | refused before the provider is asked — the P4.9 rule at a new door |
| a blank turn | asks nothing of anybody |
| a `status` body this client cannot read | the conversation keeps what it had |
| an unrecognised refusal code | read as unavailability, never as the nearest familiar code |
| a conversation with the wrong bearer credential | never completes a handshake, so never discovers a tool |
| the model answers a case that asked nothing | over the real transport: the phase permits only a read, one report row exists afterwards |

## The live smoke, and what it cost

One bounded live conversation, `us.amazon.nova-2-lite-v1:0` in `us-east-1`, run once against the
real chain. G5 item 9 asks for exactly this and no more. **It is not an evaluation and makes no
claim about the model's accuracy** — six turns say nothing about how often a verb is chosen
correctly, and no benchmark, challenger or holdout program was started.

| # | the worker says | expected | chose | tools | turn (ms) | model (ms) | in / out tokens |
|---|---|---|---|---|---|---|---|
| 1 | today's raspberry delivery didn't arrive | `REPORT` | **`REPORT`** | report, status | 4828 | 579 | 1719 / 27 |
| 2 | what do you need from me? | `STATUS` | **`STATUS`** | status | 1022 | 808 | 1721 / 27 |
| 3 | just raspberries - the strawberries came | `CLARIFY` | **`CLARIFY`** | clarify, status | 804 | 522 | 1737 / 29 |
| 4 | ok, what's the plan then? | `STATUS` | **`STATUS`** | status | 982 | 503 | 1721 / 27 |
| 5 | yes, go ahead | `CONFIRM` | **`CONFIRM`** | confirm, status | 1214 | 542 | 1740 / 28 |
| 6 | where does that leave us? | `STATUS` | **`STATUS`** | status | 839 | 533 | 1722 / 27 |

- **Model/tool sequence:** `REPORT` → `STATUS` → `CLARIFY` → `STATUS` → `CONFIRM` → `STATUS`; six
  model calls, nine tool calls, every turn within the two-call budget, one attempt each — **no
  corrective retry was needed and no answer was refused**.
- **Latency:** 9,689 ms of wall clock across six turns. Turn 1 carries the first connection and
  the first Bedrock client; the five that follow are 804–1,214 ms end to end, of which 503–808 ms
  is the model. Measured from the orchestrator, not reported by the provider.
- **Durable case state:** `EXECUTING`. Two `case_reports` rows holding the worker's words byte
  for byte, both attributed to the server-configured worker. Authorised, with nothing carried
  out.
- **Spend:** 6 model calls — **10,360 input tokens, 165 output tokens**, one run.
  **No dollar figure is published.** The account this ran under cannot call `pricing:GetProducts`,
  and Nova 2 Lite is not listed on the public Bedrock pricing page as fetched, so the rate could
  not be verified. Publishing an estimate would be an invented metric; the token counts above are
  measured and are what a rate should be applied to.

The evidence file the table is quoted from is written by the test itself
(`PP_LIVE_SMOKE_RECORD`, default `live-smoke.json`, gitignored). Nothing in it is computed by
hand.

Reproduce it with:

```
AWS_PROFILE=promisepatch PP_LLM_PROVIDER=bedrock PP_AWS_REGION=us-east-1 \
  PP_BEDROCK_MODEL_ID=us.amazon.nova-2-lite-v1:0 \
  uv run python scripts/with_local_env.py -- \
  uv run pytest apps/backend/tests/test_orchestrator_live.py -m "bedrock_live and integration"
```

## Talking to it

`pp converse` is the operator's conversational client. It connects to `PP_ORCHESTRATOR_MCP_URL`
with `PP_MCP_BEARER_TOKEN`, holds no database handle, and can affect nothing except through a
tool call. `--turn` repeats for a scripted conversation; `--show-tools` prints the verb chosen,
the tools called and the turn's latency. Against the default fake provider every turn chooses
`NONE`, which is the honest behaviour of a deployment with no model configured.

## Limitations, stated

- **A rejected preface costs the worker a turn.** Glue that claims an outcome fails the whole
  answer rather than being trimmed, so a model that phrases badly on both attempts loses that
  turn's action and the worker repeats themselves. Deliberate: a repaired sentence is one nobody
  wrote.
- **The glue gate is a word list.** It understands nothing. A model can imply completion without
  using any of its 39 words. What is guaranteed is that no *authoritative* sentence comes from
  the model at all.
- **The affirmation list is a list.** A worker who says yes in a way nobody wrote down is asked
  again.
- **One case per conversation.** `REPORT` is offered only from `NO_CASE`, so a second exception
  starts a second conversation. Revisit when the case workspace can hold more than one.
- **The follow-up read can miss a case that is still moving.** After `report`, the interpreter
  has usually not run, so the worker hears the report's own sentence and learns about the
  question on their next turn. There is no push; a conversation is turn-driven.
- **Six live turns are not a measurement.** They establish that the path holds together with a
  real model in it. Nothing here says how often Nova chooses the right verb, and no such claim
  is made anywhere.
- **`pp converse` was not itself exercised live.** It composes the same `connect` + `Orchestrator`
  path the integration and live suites drive, and its own coverage is the refusal it gives when
  no endpoint is configured. A second live conversation to exercise the argument plumbing would
  have been a second paid run for no new property, and G5 asks for one.
- **The live run needed a combined CA bundle on this workstation** (`AWS_CA_BUNDLE` naming
  certifi's roots plus the local interception root) because the profile's `credential_process`
  hop is TLS-intercepted here. That is a property of one machine, not of the code, and nothing
  about it was committed.
- Both holdouts remain sealed. P4.8 stays closed.

## Not in this slice

The bounded withdrawal (the fifth tool — `ConversationTool` has no member for it), voice, the
Telegram channel, the Alexa+ simulation, the case workspace UI, any cloud deployment, and any
benchmark program.
