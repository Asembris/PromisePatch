## 2. Resolving `TlsHostname` without owning a domain

P6.1 closed with one outstanding input: a DNS name for `TlsHostname`, because a publicly
trusted certificate cannot be issued for an `ec2-*.compute-1.amazonaws.com` name. The parameter
had no default and the stack could not be created without one.

It also had an ordering problem that no amount of supplying would fix on a *first* deploy: the
address a DNS record would have to point at is the `ElasticIp` **this stack allocates**, so
before the first deploy there is nothing to point a record at. Supplying a name in advance means
either owning a domain and pointing it at an address that does not exist yet, or deploying
twice.

The stack now derives the name from the address instead. `TlsHostname` defaults to empty; when
it is empty, a `DeriveTlsHostname` condition builds `<elastic-ip>.sslip.io` from `!Ref
ElasticIp`. sslip.io answers `a.b.c.d.sslip.io` with `a.b.c.d` for every address, so the record
exists before the host boots and Caddy's first ACME order is for a name that already resolves to
the host asking for it. Supplying a real name still works and is unchanged — the condition is
only reached by leaving the parameter empty.

**Nothing about TLS is weakened by this.** The certificate is a real, publicly trusted,
automatically issued one for the exact name clients verify; no self-signed certificate is issued
anywhere and no client is asked to skip verification. Two tests hold that line: one asserts the
derived name is built from `ElasticIp` and from no other input — a name built from anything else
would be a name somebody else controls, and the certificate would be issued to them — and one
asserts no derived output publishes an `http://` origin or a bare address.

**Honest limits of the derived name.** sslip.io is a third-party public DNS service this project
does not run; if it stops answering, the name stops resolving and certificate renewal stops with
it. The name is also as stable as the Elastic IP and no more: release the address and the name
is somebody else's. It is the right shape for a demonstration deployment and the wrong shape for
a customer-facing one, where the answer is a name the business owns pointed at the same output.

## 3. Five defects, all found by deploying and none findable without it

Every one of these was in the definition P6.1 wrote and committed, and none of them could be
found by reading it — P6.1 says so itself: "9/9 is not the same claim as *the deploy will
succeed*." This is what the difference consisted of.

### 3.1 The five the deploy found

| # | What the definition said | What AWS said | The correction |
|---|---|---|---|

| 3 | the runtime policy named the log group with `!GetAtt LogGroup.Arn` | `InstanceRole CREATE_FAILED: Unable to retrieve Arn attribute for AWS::Logs::LogGroup ... ### 3.3 One found pre-emptively

The Caddyfile defaulted its ACME contact to `admin@localhost`, and `deploy.sh` wrote an
`acme-contact` secret that nothing ever read. ACME registration validates the contact address,
and an unresolvable domain can fail the certificate order outright — which would have cost the
one thing the deployment exists to demonstrate. The contact is now wired end to end from the
parameter, and defaults to *empty* rather than to a made-up address: no contact is a valid
registration, a contact nobody can receive mail at is not.

### 3.4 Local friction worth recording

Git Bash's MSYS runtime rewrites arguments that look like absolute paths, so
`aws ssm put-parameter --name /promisepatch/prod/db-master-password` arrived at AWS as
`parameter/C:/Program Files/Git/promisepatch/prod/db-master-password`. Nothing was created and
the denial named the mangled path, which is what made it obvious. `MSYS2_ARG_CONV_EXCL=*` fixes
it and breaks `git -C /d/PromisePatch`, which then fails the clean-tree check and reports the
tree as dirty; the working setting is `MSYS2_ARG_CONV_EXCL=/promisepatch`, which excludes only
the SSM paths. This is not a repository defect and nothing was changed for it.


### 3.5 Three more the deploy found, after the stack was up

| # | What was wrong | How it showed | The correction |
|---|---|---|---|
| 8 | `docker compose up -d` re-ran `seed`, and `pp reset-demo-state` replaces every domain row | **a case reached over the deployed MCP surface was gone after one reboot**, with the database itself perfectly intact. The restart proof P6.1 designed would have failed here | `seed` is behind a compose profile, nothing depends on it, and the bootstrap's `compose run -T seed` is the only thing that starts it — once per instance |

| 10 | `HttpPutResponseHopLimit: 1` | the deployed worker's first Bedrock call returned `NoCredentialsError` **in 2 ms, having made no network request** | every process here runs in a container, the Docker bridge costs a hop, so at a limit of 1 **no container can obtain the instance role at all**. `HttpTokens: required` is the control that matters and is unchanged; the limit becomes 2, which is what AWS documents for containers on EC2. **Committed, not applied — see §7** |

Two further facts were established the same way and are recorded because both were believed
otherwise:

- **`UserData` is not a replacement trigger for `AWS::EC2::Instance`.** A stack update carrying
  a new `ImageTag` reported `UPDATE_COMPLETE`, left the instance id unchanged, and the host went
  on serving the image it first booted with. The template's comment claiming the bootstrap "runs
  again on every boot" was wrong — cloud-init's `scripts-user` is once-per-instance — and has
  been corrected to say what it does. Until it converges per boot, a definition change reaches
  the host only by replacing the instance.
- **`UserDataReplaceOnChange` is not a property of `AWS::EC2::Instance`.** Adding it failed
  validation (`extraneous key ... is not permitted`) and was removed.

## 7. The blocker, and how it was closed

Two IAM actions were missing and this credential could not grant them. **The account owner
granted both, and both are applied.** Verified read-only against the real resource ARNs with
`iam:SimulatePrincipalPolicy` before either was used — simulating against `*` returns
`implicitDeny` and means nothing:

```
PromisePatchDeveloperRole   cloudformation:ContinueUpdateRollback
                            on stack/promisepatch-prod/1d349a00-…      allowed
PromisePatchDeploymentRole  ec2:ModifyInstanceMetadataOptions
                            on instance/i-02eae57987bad0691
                            with ec2:ResourceTag/Project=promisepatch  allowed
```

The recovery then ran exactly as §7 of the previous revision predicted, with no new decision:

1. `continue-update-rollback --resources-to-skip Host` → `UPDATE_ROLLBACK_COMPLETE`. `Host` is
   skipped because its rollback was the denied call; every other resource rolled back cleanly.
2. `./deploy/deploy.sh images` → pushed at `c6e557c855f2`.
3. `./deploy/deploy.sh stack` → `UPDATE_COMPLETE`, and the host reports
   `HttpTokens: required`, `HttpPutResponseHopLimit: 2`, `HttpEndpoint: enabled`. **IMDSv2 was
   not weakened to achieve this** — the token requirement is the control against an
   application-layer request forgery and it is unchanged. The hop limit is a separate setting,
   and 1 was simply wrong for a host where everything runs in a container.
4. Rebooted, so every container re-resolved credentials rather than reusing a cached failure.

### 7.3 Nothing was weakened to get here

TLS verification is on everywhere and no self-signed certificate exists. The bearer check, the
`Origin` allowlist and the `Host` validation are where P5.1 put them, in the `mcp` process in
front of the protocol. The database is private and encrypted. There is no key pair and no
inbound 22. IMDSv2 stays required. IAM was not broadened beyond the two actions the owner
granted, each scoped to a resource its role already owned. Two further denials were routed
around *without* asking for IAM at all — the AMI parameter read and the log-group attribute
read — by making the template stop depending on a permission rather than by granting one.
