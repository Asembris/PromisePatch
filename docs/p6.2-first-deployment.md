## 2. Resolving `TlsHostname` without owning a domain

P6.1 closed with one outstanding input: a DNS name for `TlsHostname`, because a publicly
trusted certificate cannot be issued for an `ec2-*.compute-1.amazonaws.com` name. The parameter
had no default and the stack could not be created without one.

It also had an ordering problem that no amount of supplying would fix on a *first* deploy: the
address a DNS record would have to point at is the `ElasticIp` **this stack allocates**, so
before the first deploy there is nothing to point a record at. Supplying a name in advance means
either owning a domain and pointing it at an address that does not exist yet, or deploying
twice.

The stack now derives the name from the address instead. `TlsHostname` defaults to empty; when
it is empty, a `DeriveTlsHostname` condition builds `<elastic-ip>.sslip.io` from `!Ref
ElasticIp`. sslip.io answers `a.b.c.d.sslip.io` with `a.b.c.d` for every address, so the record
exists before the host boots and Caddy's first ACME order is for a name that already resolves to
the host asking for it. Supplying a real name still works and is unchanged — the condition is
only reached by leaving the parameter empty.

**Nothing about TLS is weakened by this.** The certificate is a real, publicly trusted,
automatically issued one for the exact name clients verify; no self-signed certificate is issued
anywhere and no client is asked to skip verification. Two tests hold that line: one asserts the
derived name is built from `ElasticIp` and from no other input — a name built from anything else
would be a name somebody else controls, and the certificate would be issued to them — and one
asserts no derived output publishes an `http://` origin or a bare address.

**Honest limits of the derived name.** sslip.io is a third-party public DNS service this project
does not run; if it stops answering, the name stops resolving and certificate renewal stops with
it. The name is also as stable as the Elastic IP and no more: release the address and the name
is somebody else's. It is the right shape for a demonstration deployment and the wrong shape for
a customer-facing one, where the answer is a name the business owns pointed at the same output.

## 3. Five defects, all found by deploying and none findable without it

Every one of these was in the definition P6.1 wrote and committed, and none of them could be
found by reading it — P6.1 says so itself: "9/9 is not the same claim as *the deploy will
succeed*." This is what the difference consisted of.

### 3.1 The five the deploy found

| # | What the definition said | What AWS said | The correction |
|---|---|---|---|
| 1 | the bootstrap script escaped its 18 shell variables as `$${NAME}` | `Template format error: Unresolved resource dependencies [COMPOSE_VERSION, PORT, HOST, ...]` — the template was rejected before one resource was created | `Fn::Sub`'s escape is `${!NAME}`; `$${NAME}` is docker compose's and CodeBuild's. Rewrote all 31 |
| 2 | `HostAmiId` resolved through `AWS::SSM::Parameter::Value<AWS::EC2::Image::Id>` from the AWS-published AMI parameter | `PromisePatchDeploymentRole ... is not authorized to perform: ssm:GetParameters on .../aws/service/ami-amazon-linux-latest/...` | the deployment role is scoped to this project's own parameters. `deploy.sh` now resolves the AMI with the `ec2:DescribeImages` the submitting identity already holds, and passes it in. No AMI is pinned in git either way |
| 3 | the runtime policy named the log group with `!GetAtt LogGroup.Arn` | `InstanceRole CREATE_FAILED: Unable to retrieve Arn attribute for AWS::Logs::LogGroup ... Access denied for operation 'logs:DescribeLogGroups'` | **the same wrongly shaped grant P6.1 fixed on the developer role, sitting unnoticed in the deployment role.** `DescribeLogGroups` is evaluated account-wide and a grant scoped to `log-group:/promisepatch/*` never authorizes it. The ARN is fully determined by the name the stack chose, so it is now built with `Fn::Sub` and needs no permission at all |
| 4 | a rule described itself as `PostgreSQL to the stack's database.` | `Invalid rule description. Valid descriptions are strings ... from the following set: a-zA-Z0-9. _-:/()#,@[]+=&;{}!$*` | EC2's description charset has no apostrophe. Prose written for a reader is exactly where one comes from |
| 5 | `BackupRetentionPeriod: 7` | `The specified backup retention period exceeds the maximum available to free tier customers` | an account-level constraint, not a defect. Retention is now a parameter with the week as its default and a floor of 1, so lowering it is a recorded deployment decision rather than an edited constant |

Three of the five are failures of *permission shape* or *syntax* that no amount of reading
catches, and two of them — 2 and 3 — are the preflight's own limitation showing up exactly where
P6.1 predicted it would: twelve mutating requirements were `DECLARED` rather than tested, and the
denials that stopped this deploy were both in that untested set.

### 3.2 The two found by reading the definition against the code, before deploying

### 3.3 One found pre-emptively

The Caddyfile defaulted its ACME contact to `admin@localhost`, and `deploy.sh` wrote an
`acme-contact` secret that nothing ever read. ACME registration validates the contact address,
and an unresolvable domain can fail the certificate order outright — which would have cost the
one thing the deployment exists to demonstrate. The contact is now wired end to end from the
parameter, and defaults to *empty* rather than to a made-up address: no contact is a valid
registration, a contact nobody can receive mail at is not.

### 3.4 Local friction worth recording

Git Bash's MSYS runtime rewrites arguments that look like absolute paths, so
`aws ssm put-parameter --name /promisepatch/prod/db-master-password` arrived at AWS as
`parameter/C:/Program Files/Git/promisepatch/prod/db-master-password`. Nothing was created and
the denial named the mangled path, which is what made it obvious. `MSYS2_ARG_CONV_EXCL=*` fixes
it and breaks `git -C /d/PromisePatch`, which then fails the clean-tree check and reports the
tree as dirty; the working setting is `MSYS2_ARG_CONV_EXCL=/promisepatch`, which excludes only
the SSM paths. This is not a repository defect and nothing was changed for it.


### 3.5 Three more the deploy found, after the stack was up

| # | What was wrong | How it showed | The correction |
|---|---|---|---|
| 8 | `docker compose up -d` re-ran `seed`, and `pp reset-demo-state` replaces every domain row | **a case reached over the deployed MCP surface was gone after one reboot**, with the database itself perfectly intact. The restart proof P6.1 designed would have failed here | `seed` is behind a compose profile, nothing depends on it, and the bootstrap's `compose run -T seed` is the only thing that starts it — once per instance |
| 9 | an unlisted `Host` got Caddy's "no site matched" default: an **empty 200** | the smoke check's `host-refused` failed with `status 200, expected 421`. The request never reached the protocol, so nothing was exposed — the status simply lied about it | a catch-all `:443` site that answers `421`. The named site is more specific and still wins; the MCP server's own `Host`, `Origin` and bearer checks are untouched |
| 10 | `HttpPutResponseHopLimit: 1` | the deployed worker's first Bedrock call returned `NoCredentialsError` **in 2 ms, having made no network request** | every process here runs in a container, the Docker bridge costs a hop, so at a limit of 1 **no container can obtain the instance role at all**. `HttpTokens: required` is the control that matters and is unchanged; the limit becomes 2, which is what AWS documents for containers on EC2. **Committed, not applied — see §7** |

Two further facts were established the same way and are recorded because both were believed
otherwise:

- **`UserData` is not a replacement trigger for `AWS::EC2::Instance`.** A stack update carrying
  a new `ImageTag` reported `UPDATE_COMPLETE`, left the instance id unchanged, and the host went
  on serving the image it first booted with. The template's comment claiming the bootstrap "runs
  again on every boot" was wrong — cloud-init's `scripts-user` is once-per-instance — and has
  been corrected to say what it does. Until it converges per boot, a definition change reaches
  the host only by replacing the instance.
- **`UserDataReplaceOnChange` is not a property of `AWS::EC2::Instance`.** Adding it failed
  validation (`extraneous key ... is not permitted`) and was removed.

### 4.6 Logs, and the deterministic spine

Seven container log streams reach `/promisepatch/prod`: `migrate`, `seed`, `api`, `worker`,
`mcp`, `order-simulator`, `caddy`. The worker steps the deployed loop actually ran:


## 6. The derived hostname, honestly

`sslip.io` is a third-party public DNS service this project does not run. If it stops answering,
the name stops resolving and certificate renewal stops with it. The name is exactly as stable as
the Elastic IP: release the address and the name belongs to whoever gets it next. It is the right
shape for a deployment meant to be reached and read, and the wrong shape for a customer-facing
one — where the answer is a name the business owns, pointed at the same `ElasticIp` output, with
`TlsHostname` supplied instead of left empty. The template is identical either way.

## 7. The one blocker, stated exactly

**Two IAM actions are missing, and this credential cannot grant them.** Both are already written
into the committed policy documents; neither is applied.

1. `deploy/policies/deployment-role-policy.json`, statement `OneHostAndTheVolumeItBootsFrom`,
   add **`ec2:ModifyInstanceMetadataOptions`** — same `instance/*` resource and
   `Project=promisepatch` tag condition as the reboot/stop/start actions already there. Without
   it the hop-limit fix cannot be applied to a running host, and every container stays unable to
   use the instance role.
2. `deploy/policies/developer-role-delta.json`, statement `StackIsTheOnlyMutationPath`, add
   **`cloudformation:ContinueUpdateRollback`** — same `stack/promisepatch-*/*` resource. The
   stack is in `UPDATE_ROLLBACK_FAILED` because the update in (1) was denied mid-flight, and
   from that state no further update is possible without this action.

Neither broadens anything beyond the resources these roles already own, and neither touches the
`Deny` fences on `iam:PassRole` or on IAM mutation.

With both applied, the remaining sequence is four commands and needs no new decision:

```bash
aws cloudformation continue-update-rollback --stack-name promisepatch-prod \
  --resources-to-skip Host --role-arn arn:aws:iam::<ACCOUNT_ID>:role/PromisePatchDeploymentRole
./deploy/deploy.sh images
./deploy/deploy.sh stack     # applies HttpPutResponseHopLimit: 2
./deploy/deploy.sh smoke
```

Then force one semantic step and read the log back: the same
`"the chiller packed in overnight and the berries are all mush"` report should produce
`semantic.answered` with `provider=bedrock` and a real `model_id`, where it now produces
`semantic.unavailable`.

**Nothing in this slice was worked around by weakening security.** TLS verification is on
everywhere, the bearer check, `Origin` allowlist and `Host` validation are where P5.1 put them,
the database is private and encrypted, there is no key pair and no inbound 22, and IMDSv2 stays
required. Two blockers were routed around *without* asking for IAM — the AMI parameter read and
the log-group attribute read — by having the template stop depending on a permission rather than
by granting one.
